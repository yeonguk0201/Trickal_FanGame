# Ship

이번 작업의 변경을 검증 → 커밋 → 푸시 → PR 순서로 올린다. 규칙의 기준은 `AGENTS.md`의 "커밋과 PR", "검증과 문서화" 절이다.
단계가 실패하면 그 자리에서 멈추고 원인과 출력을 보고한다. 실패를 우회해서 다음 단계로 넘어가지 않는다.

인자: `/ship` 뒤에 적은 말은 커밋 범위나 메시지에 대한 힌트로 쓴다(예: `/ship 문서만`, `/ship 푸시는 하지 마`).

## 1. 변경 범위 확인

```bash
git status --short
git branch --show-current
git log --oneline -5
```

- 현재 브랜치가 `main`이면 멈춘다. `dev/<주차 또는 주제>` 브랜치 이름을 제안하고, 사용자가 동의하면 브랜치를 만든 뒤 계속한다.
  (`.claude/hooks/protect-main.js` 훅도 `main` 커밋·푸시를 거부한다.)
- 변경 파일을 **이번 작업의 것**과 **그 밖의 것**으로 나눈다. 사용자는 같은 작업 트리에서 병렬로 작업하므로, 이 대화에서
  만들거나 고치지 않은 변경은 커밋에 넣지 않고 되돌리지도 않는다. 어느 쪽인지 불분명한 파일은 사용자에게 묻는다.
- 이미 스테이징된 변경이 있으면 사용자가 고른 것이므로 그대로 존중한다. 이번 작업과 다른 내용이면 함께 커밋할지 묻는다.
- 서로 관련 없는 작업이 섞여 있으면 커밋을 나눈다(조각 ID 단위).

## 2. 사전 점검

`pre-commit-check` 스킬을 실행한다. FAIL이 있으면 멈추고 보고한다. 특히 다음을 확인한다.

- 새 Unity 에셋·스크립트의 `.meta`가 함께 있고, 기존 GUID가 바뀌지 않았다.
- 텍스트 파일이 UTF-8이다.
- Item / Character / Run ID나 `ItemEffectType` 같은 계약을 바꿨다면 Backend 카탈로그·Unity·문서가 서로 맞는다
  (필요하면 `contract-drift-check` 스킬).
- 비밀 값(`.env`, 토큰, 키)이나 `Library/`, `node_modules/`, 로그 같은 생성물이 커밋 대상에 없다.

## 3. 검증 실행

변경된 영역에 해당하는 것만 실행한다. 이 대화에서 **같은 변경에 대해 이미 통과한 검증은 다시 돌리지 않고** 그 결과를 쓴다.
그 뒤 코드가 바뀌었다면 다시 실행한다.

| 변경 영역 | 실행 |
|---|---|
| `backend/` | `pnpm test`, 계약·빌드에 영향이 있으면 `pnpm build` |
| `web/` | `pnpm lint`, 필요 시 `pnpm build` |
| `game/` | 해당 조각의 검증기 배치(`unity-verification-runner` 스킬로 목록 확인). 권한이 허용된 실행으로 요청한다 |
| `docs/`만 | 검증 없음 |

- Unity가 같은 프로젝트를 열고 있어 배치가 잠기면 코드 실패가 아니다. 실행하지 못했다고 보고하고, 메뉴 경로와 기대 결과를
  수동 확인 항목으로 남긴다.
- 실행하지 못한 검증을 통과한 것처럼 적지 않는다.

## 4. 커밋

- 파일은 이름을 지정해 스테이징한다. `git add -A`나 `git add .`는 쓰지 않는다.
- 제목: `type(scope): 영어 요약 (조각 ID)`. type은 `feat`, `fix`, `tune`, `docs`, `refactor`, `test`, `chore` 중 하나.
  scope와 조각 ID는 해당할 때만 붙인다. 최근 `git log`의 문체를 따른다.
- 본문: 무엇을 왜 바꿨는지와, 읽는 사람이 알아야 할 동작 변화를 짧은 문단으로 쓴다. 파일 목록을 나열하지 않는다.
- 훅을 건너뛰지 않는다(`--no-verify` 금지). 기존 커밋을 고치기보다 새 커밋을 만든다.
- 시스템이 지정한 attribution 줄이 있으면 메시지 끝에 붙인다.

커밋 후 `git status --short`로 남은 변경이 의도한 것(제외한 병렬 작업)뿐인지 확인한다.

## 5. 푸시

```bash
git push -u origin <현재 브랜치>
```

- `main`으로는 푸시하지 않는다. 강제 푸시(`--force`)는 사용자가 명시적으로 요청한 경우에만 한다.
- 원격이 앞서 있어 거부되면 멈추고 상황을 보고한다. 임의로 rebase나 merge를 하지 않는다.

## 6. PR

```bash
gh pr list --head <현재 브랜치> --state open
```

- **열린 PR이 있으면** 푸시로 이미 갱신됐다. PR 주소를 알려 주고, 본문의 요약·검증 항목이 새 커밋 때문에 틀려졌다면
  고칠 내용을 제안한다(`gh pr edit`은 사용자가 동의한 뒤).
- **열린 PR이 없으면** PR을 만들지 묻는다. 만들기로 하면:
  - base는 `main`. 제목은 커밋 제목과 같은 형식.
  - 본문은 `.github/pull_request_template.md`의 절을 그대로 채운다. `git log main..HEAD`와 `git diff main...HEAD --stat`로
    PR 전체 범위를 확인하고 쓴다(마지막 커밋만이 아니다).
  - 검증 체크박스는 실제로 실행해 통과한 것만 체크한다. 확인하지 못한 수동 항목은 "대기"로 적는다.
  - 본문은 UTF-8 파일로 써서 `gh pr create --base main --head <브랜치> --title "..." --body-file <파일>`로 만든다.
- `gh`가 없거나 로그인되어 있지 않으면 `https://github.com/<owner>/<repo>/compare/main...<브랜치>?expand=1` 주소와
  작성한 본문 파일 경로를 알려 준다.
- PR을 병합하지 않는다. 병합은 사용자가 한다.

## 7. 보고

짧게 정리한다.

- 커밋 해시와 제목, 푸시한 브랜치, PR 주소(있으면)
- 실행한 검증과 결과, 실행하지 못한 검증과 이유
- 커밋에서 제외한 변경(병렬 작업 등)
- 사용자가 직접 확인해야 할 것(수동 화면 확인, seed 재실행 등)
