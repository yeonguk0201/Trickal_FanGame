# 게임 디자인

## 1. 게임 개요

### 장르

**2D 탑다운 로그라이크 액션 슈팅**

아이작 스타일의 게임 진행 구조를 참고하여, 플레이어가 매번 하나의 Run을 진행하면서 방을 탐색하고 적을 처치하며 아이템을 획득하고 최종 보스를 목표로 진행한다.

### 핵심 특징

- 짧은 플레이 세션
- 방 단위 전투
- 층 단위 진행
- 랜덤 / 절차적 요소
- 아이템 획득과 빌드 구성
- 아이템 간 시너지
- 보스 전투
- 클리어 또는 사망으로 Run 종료
- Run 결과를 서버에 기록
- 기록된 데이터를 웹에서 전적 및 통계로 조회

---

# 2. 게임의 핵심 목표

본 프로젝트의 게임 부분에서 가장 중요한 목표는 **대규모 콘텐츠를 만드는 것이 아니라 하나의 완성된 로그라이크 플레이 루프를 만드는 것**이다.

플레이어가 다음 흐름을 자연스럽게 경험할 수 있어야 한다.

```text
게임 실행
    ↓
캐릭터 선택
    ↓
Run 시작
    ↓
층 진입
    ↓
방 탐색
    ↓
일반 몬스터 전투
    ↓
방 클리어
    ↓
아이템 / 보상 획득
    ↓
다음 방
    ↓
반복
    ↓
층 보스
    ↓
다음 층
    ↓
반복
    ↓
최종 보스
    ↓
클리어 / 사망
    ↓
Run 종료
    ↓
플레이 데이터 서버 전송
```

---

# 3. 플레이어 경험

## 3.1 기본 게임 흐름

플레이어는 게임을 시작한 후 캐릭터를 선택하고 하나의 Run을 시작한다.

하나의 Run은 여러 개의 층으로 구성되며, 각 층에는 여러 개의 방이 존재한다.

각 방에서는 일반적으로 적을 처치해야 다음 방으로 이동할 수 있다.

플레이어는 방을 진행하면서 아이템을 획득하고 자신의 능력을 강화한다.

각 층의 마지막에는 보스가 존재하며, 보스를 처치하면 다음 층으로 이동한다.

최종 층의 보스를 처치하면 Run을 클리어한다.

플레이어의 HP가 0이 되면 Run은 사망으로 종료된다.

---

# 4. Run 구조

## 4.1 Run이란?

**Run**은 플레이어가 게임을 시작하여 클리어하거나 사망할 때까지의 하나의 플레이 기록을 의미한다.

```text
Run
├── 시작
├── 캐릭터 선택
├── 1층
│   ├── 방
│   ├── 전투
│   ├── 아이템
│   └── 보스
├── 2층
│   ├── 방
│   ├── 전투
│   ├── 아이템
│   └── 보스
├── 3층
│   ├── 방
│   ├── 전투
│   ├── 아이템
│   └── 최종 보스
└── 클리어 / 사망
```

Run이 종료되면 결과 데이터를 생성하여 Backend API로 전송한다.

---

# 5. 게임 진행 구조

## 5.1 전체 구조

MVP에서는 총 **3개 층**을 기본 구성으로 한다.

```text
Run
 │
 ├── Floor 1
 │    ├── Room
 │    ├── Room
 │    ├── Item / Reward
 │    └── Boss
 │
 ├── Floor 2
 │    ├── Room
 │    ├── Room
 │    ├── Item / Reward
 │    └── Boss
 │
 └── Floor 3
      ├── Room
      ├── Room
      ├── Item / Reward
      └── Final Boss
```

각 층은 여러 개의 방으로 구성된다.

방의 정확한 개수와 생성 규칙은 구현 단계에서 조정할 수 있지만, 플레이어가 단순히 한 방씩 직선적으로 진행하는 느낌보다는 **탐색과 선택이 존재하는 구조**를 목표로 한다.

---

# 6. 캐릭터 선택

## 6.1 기본 방향

MVP에서는 **플레이 가능한 캐릭터를 1종으로 제한한다.**

다만 게임 시작 시 캐릭터를 선택하는 화면은 구현한다.

```text
캐릭터 선택

┌──────────────┐
│              │
│  Character A │
│              │
│   [선택]     │
└──────────────┘

※ 향후 캐릭터 추가 가능
```

현재는 선택 가능한 캐릭터가 하나뿐이지만, 향후 캐릭터가 추가되더라도 게임 시스템을 크게 변경하지 않는 것을 목표로 한다.

---

## 6.2 캐릭터 확장 방향

MVP:

```text
Character A
└── 플레이 가능
```

향후:

```text
Character A
├── 플레이 가능

Character B
├── 플레이 가능

Character C
└── 플레이 가능
```

따라서 캐릭터 관련 데이터는 특정 캐릭터 하나에 강하게 결합하지 않고 확장 가능한 형태로 설계한다.

### 캐릭터가 가질 수 있는 기본 정보

- Character ID
- 이름
- 기본 HP
- 이동 속도
- 공격력
- 공격 속도
- 공격 방식
- 기본 스킬
- 기본 능력치

---

# 7. 플레이어 조작

## 7.1 이동

플레이어는 키보드를 사용하여 캐릭터를 이동시킨다.

기본 방향:

```text
W
↑

A ← Player → D

S
↓
```

정확한 입력 방식은 Unity Input System 구현 단계에서 결정한다.

---

## 7.2 공격

플레이어는 이동하면서 적을 공격할 수 있어야 한다.

기본 공격 방식은 **탑다운 슈팅 방식**을 사용한다.

예상 구조:

```text
이동 방향
     ↓
Player → 공격
     ↓
Projectile
     ↓
Enemy
     ↓
Damage
```

공격 방식의 세부 구현은 프로토타입 단계에서 결정한다.

---

# 8. Room

## 8.1 방의 역할

방은 게임 플레이의 기본적인 전투 단위다.

플레이어가 새로운 방에 진입하면 적이 등장하고, 적을 모두 처치하면 방이 클리어된다.

기본 흐름:

```text
방 입장
   ↓
적 스폰
   ↓
전투
   ↓
모든 적 처치
   ↓
방 클리어
   ↓
보상 / 다음 방
```

---

## 8.2 기본 방 상태

방은 최소한 다음 상태를 가질 수 있다.

```text
RoomState

LOCKED
  ↓
ENTERED
  ↓
COMBAT
  ↓
CLEARED
```

예:

```text
플레이어 방 진입
      ↓
적 생성
      ↓
문 잠금
      ↓
전투
      ↓
적 전멸
      ↓
문 해제
      ↓
다음 방 이동
```

---

# 9. Room 종류

MVP에서는 지나치게 많은 방 종류를 만들지 않는다.

기본적으로 다음과 같은 방을 사용한다.

### 9.1 일반 전투방

가장 기본적인 방.

```text
입장
 ↓
일반 몬스터 등장
 ↓
전투
 ↓
전멸
 ↓
방 클리어
```

### 9.2 아이템 / 보상방

전투 또는 특정 조건을 만족한 후 아이템을 획득할 수 있는 공간.

### 9.3 보스방

각 층의 마지막에 위치한다.

```text
보스 등장
 ↓
보스 전투
 ↓
보스 처치
 ↓
층 클리어
```

필요할 경우 개발 과정에서 상점, 이벤트방 등의 추가 방 종류를 고려할 수 있다.

---

# 10. Floor

## 10.1 층의 역할

여러 개의 방을 하나의 진행 단위로 묶는다.

각 층은 일반 방을 진행한 후 마지막에 보스방을 거치는 구조를 기본으로 한다.

```text
Floor Start
    ↓
Room
    ↓
Room
    ↓
Room
    ↓
Boss Room
    ↓
Boss Defeated
    ↓
Floor Clear
```

---

## 10.2 MVP 층 구성

총 3개 층을 사용한다.

```text
Floor 1
└── Boss

Floor 2
└── Boss

Floor 3
└── Final Boss
```

각 층의 테마와 난이도는 점진적으로 상승한다.

### 기본 난이도 방향

```text
Floor 1
쉬운 적
낮은 체력
기본적인 패턴

      ↓

Floor 2
적 종류 증가
공격 패턴 증가
난이도 상승

      ↓

Floor 3
강한 적
복합적인 패턴
최종 보스
```

---

# 11. 절차적 / 랜덤 요소

로그라이크의 반복 플레이 재미를 위해 일부 요소는 랜덤하게 구성한다.

### 랜덤화 대상

- 방 배치
- 방 연결
- 일반 몬스터 구성
- 적 스폰 위치
- 아이템 등장
- 아이템 획득 순서
- 일부 이벤트

단, **완전한 랜덤보다 플레이 가능한 범위를 보장하는 구조**를 우선한다.

---

# 12. Monster

## 12.1 기본 구조

MVP에서는 약 **3~5종의 일반 몬스터**를 구현한다.

각 몬스터는 서로 다른 공격 또는 이동 패턴을 갖도록 구성한다.

예:

```text
Monster A
└── 플레이어 추적

Monster B
└── 원거리 공격

Monster C
└── 돌진 공격

Monster D
└── 특정 방향 공격

Monster E
└── 특수 패턴
```

실제 몬스터 종류와 패턴은 구현 단계에서 확정한다.

---

## 12.2 몬스터 기본 상태

```text
Spawn
  ↓
Idle / Detect
  ↓
Chase / Attack
  ↓
Hit
  ↓
Dead
```

---

# 13. Boss

## 13.1 기본 방향

각 층의 마지막에는 보스가 존재한다.

MVP에서는 **1~2종의 보스**를 구현한다.

```text
Floor 1
└── Boss

Floor 2
└── Boss

Floor 3
└── Final Boss
```

필요한 경우 하나의 보스를 여러 층에서 강화된 형태로 사용하는 것도 허용한다.

---

## 13.2 보스 전투

일반 몬스터보다 복잡한 공격 패턴을 가진다.

예:

```text
Boss
├── 기본 공격
├── 범위 공격
├── 투사체 공격
├── 이동 패턴
└── 특수 패턴
```

최종 보스는 일반 보스보다 높은 난이도와 복합적인 패턴을 갖는다.

---

# 14. Item

## 14.1 기본 방향

아이템은 플레이어의 능력을 변화시키고 Run마다 다른 빌드를 구성하게 하는 핵심 요소다.

MVP에서는 **약 10종의 아이템**을 구현한다.

---

## 14.2 아이템 효과 유형

아이템은 다음과 같은 효과를 가질 수 있다.

### 능력치 증가

```text
공격력 +
HP +
이동 속도 +
공격 속도 +
```

### 공격 변화

```text
투사체 크기 증가
투사체 개수 증가
공격 방식 변경
공격 범위 증가
```

### 특수 효과

```text
적 처치 시 추가 효과
피격 시 효과
특정 조건에서 추가 공격
```

---

# 15. Item Synergy

아이템 시스템의 핵심 재미 요소 중 하나로 **아이템 간 시너지**를 구현한다.

예:

```text
Item A
공격력 증가

+

Item B
투사체 증가

        ↓

공격력이 증가된 투사체를 여러 발 발사
```

또는:

```text
Item C
공격 속도 증가

+

Item D
투사체 크기 증가

        ↓

빠르고 큰 투사체
```

MVP에서는 모든 아이템에 복잡한 시너지를 부여하기보다 **일부 아이템 조합에서 명확한 시너지 효과가 발생하도록 설계**한다.

---

# 16. Item 획득 및 Build

플레이어는 Run을 진행하면서 아이템을 획득한다.

```text
Run Start
   ↓
기본 능력치
   ↓
Item A
   ↓
Build 변화
   ↓
Item B
   ↓
Synergy 발생
   ↓
Item C
   ↓
최종 Build
```

따라서 Run 데이터에는 단순히 어떤 아이템을 가지고 있었는지만 기록하는 것이 아니라 **아이템을 획득한 순서와 시점**도 기록할 수 있도록 한다.

---

# 17. 보상

방 또는 층을 클리어하면 플레이어에게 보상이 제공될 수 있다.

MVP에서는 보상 시스템을 복잡하게 만들지 않고 다음 범위에서 구현한다.

- 아이템
- 회복
- 다음 방으로 이동

향후 필요에 따라 추가 보상을 도입할 수 있다.

---

# 18. 게임 종료

Run은 다음 두 가지 경우에 종료된다.

## 18.1 사망

플레이어 HP가 0이 되면 Run을 종료한다.

```text
Player HP = 0
      ↓
Death
      ↓
Run 종료
      ↓
결과 데이터 생성
      ↓
Server 전송
```

기록 대상:

- 도달 층
- 플레이 시간
- 처치 수
- 획득 아이템
- 사망 원인
- 사용 캐릭터

---

## 18.2 클리어

최종 보스를 처치하면 Run을 클리어한다.

```text
Final Boss
    ↓
Boss Defeated
    ↓
Game Clear
    ↓
Run 종료
    ↓
결과 데이터 생성
    ↓
Server 전송
```

기록 대상:

- 도달 층
- 플레이 시간
- 처치 수
- 획득 아이템
- 사용 캐릭터
- 클리어 여부

---

# 19. Run 결과 데이터

Run 종료 시 게임에서 생성되는 주요 데이터를 정의한다.

```text
Run Result

- runId
- userId
- characterId
- startedAt
- endedAt
- playTime
- reachedFloor
- clear
- killCount
- deathReason
- items
```

아이템은 별도의 데이터로 관리할 수 있다.

```text
RunItem

- runId
- itemId
- floor
- acquiredAt
- order
```

구체적인 데이터베이스 구조는 `06-database.md`에서 정의한다.

# 20. 난이도 설계

난이도는 층이 올라갈수록 점진적으로 상승한다.

### 주요 난이도 요소

- 몬스터 HP
- 몬스터 공격력
- 몬스터 이동 속도
- 몬스터 수
- 공격 패턴
- 방 구성
- 보스 패턴

기본 방향:

```text
Floor 1
난이도 ★

Floor 2
난이도 ★★

Floor 3
난이도 ★★★
```

단순히 적의 체력만 증가시키기보다는 **새로운 패턴과 조합을 통해 난이도를 높이는 것**을 우선한다.

# 22. 게임 플레이 목표 시간

포트폴리오 프로젝트의 범위를 고려하여 한 번의 Run이 지나치게 길어지지 않도록 한다.

### 목표

**한 Run당 약 10분 내외**

단, 실제 플레이 테스트 결과에 따라 조정한다.

목표는 긴 플레이 타임이 아니라 다음 경험을 짧은 시간 안에 보여주는 것이다.

```text
 ↓
전투
 ↓
아이템 획득
 ↓
빌드 변화
 ↓
층 진행
 ↓
보스
 ↓
클리어 / 사망
 ↓
전적 기록
```

# 28. 게임 디자인 핵심 원칙

## 28.1 콘텐츠보다 플레이 루프

게임의 콘텐츠 양을 늘리는 것보다 다음 루프가 완성되는 것을 우선한다.

```text
방 진입
 ↓
전투
 ↓
보상
 ↓
빌드 강화
 ↓
다음 방
 ↓
보스
 ↓
다음 층
```

---

## 28.2 캐릭터는 1종으로 제한

MVP에서는 캐릭터를 1종으로 제한하여 개발 범위를 통제한다.

다만 캐릭터 선택창과 캐릭터 데이터 구조는 향후 추가 캐릭터를 고려하여 설계한다.

---

## 28.3 데이터가 남는 게임

모든 게임 시스템을 구현할 때 **웹 서비스에서 어떤 데이터를 사용할 수 있는가**를 고려한다.

게임 플레이 데이터가 단순히 게임 내부에서 사라지지 않고 Run 기록으로 남도록 한다.

---

## 28.4 짧고 완성도 있는 경험

목표 플레이 시간은 약 10분 내외로 설정한다.

게임의 규모를 크게 만드는 것보다 짧은 시간 안에 다음 경험을 제공하는 것을 우선한다.

> **캐릭터 선택 → 전투 → 아이템 → 빌드 변화 → 층 진행 → 보스 → 클리어/사망 → 전적 기록**
