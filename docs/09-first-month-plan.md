## 1. 이 문서의 역할

`02-roadmap.md`는 프로젝트 전체의 Phase와 범위를 정의한다. 이 문서는 그중 지금부터 한 달 동안 실제로 진행할 작업을 주차별 체크포인트로 나눈 실행 계획이다.

- 날짜는 작업의 우선순위를 정하기 위한 기준이며 절대적인 마감일이 아니다.
- 작업을 시작한 것이 아니라 각 주차의 **완료 조건(Definition of Done)**을 만족해야 완료로 본다.
- 일정이 밀리면 선택 작업을 먼저 제외한다. 테스트와 관통 검증은 생략하지 않는다.
- 새 기능이 떠올라도 현재 주차의 완료 조건과 직접 관계없으면 백로그에 기록하고 구현은 미룬다.
- 매주 마지막 날에 실제 소요 시간과 막힌 원인을 기록하고 다음 주 범위를 조정한다.

## 2. 첫 달의 최종 완료 조건

2026-09-14까지 다음 흐름을 한 번 이상 직접 확인한다.

```text
Unity에서 Run 시작
  → 이동과 기본 공격
  → 일반 적과 방 전투
  → 보스 처치 또는 플레이어 사망
  → Run Result 생성
  → POST /api/runs
  → PostgreSQL 저장
  → Web에서 최근 전적 확인
```

최종 데모의 콘텐츠 범위는 작게 유지한다.

- 캐릭터 1종
- 기본 공격 1종
- 일반 적 1종
- 일반 방 1~2개
- 보스 1종, 단순 패턴 1개
- 아이템은 없어도 됨. 시간이 남으면 1종만 추가
- 임시 그래픽과 기본 UI 허용

# 5. 2주차 — 플레이어와 전투 코어

## 기간

2026-08-25(화) ~ 2026-08-31(월)

## 목표

임시 오브젝트만 사용해도 플레이어가 움직이고, 공격하고, 적을 죽일 수 있는 전투의 최소 단위를 완성한다.

## 권장 진행 순서

```text
입력
  → 이동
  → 기본 공격
  → 충돌/피격 판정
  → 피해 계산
  → 적 HP 감소
  → 적 사망
```

## 필수 작업

### Player

- [x] 입력과 이동 로직 구현
- [x] 이동 속도를 코드에 흩어진 상수가 아닌 설정값으로 관리
- [x] 플레이어 HP와 피격 처리 구현
- [x] HP가 0이 되면 사망 상태로 전환
- [x] 사망 중 입력과 공격 차단

### Combat

- [x] 기본 공격 구현
- [x] 공격 방향과 공격 주기 정의
- [x] 공격 판정과 데미지 전달 구현
- [x] 같은 공격이 의도치 않게 여러 번 적중하지 않는지 확인

### 테스트용 Enemy

- [x] HP를 가진 고정 표적 또는 단순 적 구현
- [x] 피격 반응을 Console 또는 임시 UI로 확인
- [x] HP가 0이 되면 사망하고 전투 대상에서 제거

### 검증과 정리

- [x] Play Mode에서 이동·공격·피격·사망을 반복 확인
- [x] 핵심 상태 전환에 중복 실행 문제가 없는지 확인
- [x] Input, Player, Combat의 책임이 한 클래스에 과도하게 몰리지 않았는지 점검

## 완료 조건

> Unity Play Mode에서 플레이어가 이동하고 기본 공격으로 적의 HP를 줄여 사망시킬 수 있다. 플레이어도 피해를 받아 사망하며, 사망 후에는 조작되지 않는다.

## 선택 작업

- [ ] 간단한 피격 깜빡임 또는 넉백
- [ ] 공격 효과음과 임시 파티클
- [ ] HP 디버그 UI
- [ ] 오브젝트 풀링

오브젝트 풀링은 실제 생성/파괴가 문제가 될 때 도입해도 늦지 않다.

## 주간 회고

- 실제 작업 시간: 미기록
- 가장 오래 걸린 문제: Unity 6의 `ContactFilter2D` API 차이, Kinematic Rigidbody2D의 벽 통과, 투사체 간 충돌
- 다음 주에 반영할 점: 방 구조를 먼저 고정하고, 적 등록·스폰·전멸 감지를 Room이 소유하도록 구현한다.

### 완료 작업 기록

- Health → Run 저장 → 전적 조회 관통 검증 완료
- `Health` 공통 체력, Player 이동·피격·사망 차단, 근접 공격 구현
- 방향키 조준과 WASD 이동을 분리해 카이팅 가능한 조작 구현
- 플레이어 추적·접촉 피해·사망 제거를 갖춘 테스트 적 구현
- 기본 원거리 투사체와 플레이어 속도 상속 구현
  - `투사체 속도 = 발사 방향 × 기본 속도 + 플레이어 속도 × 관성 계수`
- Player / Enemy / PlayerProjectile 레이어와 충돌 행렬 설정
- 벽 충돌, 투사체 제거, 적 벽 충돌, 플레이어 사망 후 조작 차단을 Play Mode에서 확인

랜덤 생성은 첫 달 필수 범위가 아니다. 고정된 방 순서로 전체 루프부터 검증한다.

# 7. 4주차 — 최소 Run 수직 슬라이스

## 기간

2026-09-08(화) ~ 2026-09-14(월)

## 목표

앞선 시스템을 하나의 시작과 끝이 있는 Run으로 연결하고, 실제 플레이 결과를 1주차에 만든 파이프라인으로 전송한다.

## 권장 진행 순서

```text
Run 시작
  → 일반 방 진행
  → 보스방 진입
  → 보스 전투
  → 클리어 또는 사망
  → 결과 스냅샷 생성
  → API 전송
  → Web 확인
```

## 필수 작업

### Boss

- [x] 보스 HP와 사망 처리 구현
- [x] 단순하지만 피할 수 있는 공격 패턴 1개 구현
- [x] 보스방 입장과 전투 시작 연결
- [x] 보스 사망 시 Run 클리어 처리

### Run 상태

- [x] Run 시작 시간과 종료 시간 기록
- [x] 플레이 시간 계산
- [x] 현재 층, 처치 수, 클리어 여부 기록
- [x] 플레이어 사망 시 `deathReason`과 함께 Run 종료
- [x] 보스 처치 시 `deathReason` 없이 Run 종료
- [x] 종료 처리가 두 번 호출되어 중복 전송되지 않도록 방지

### 실제 데이터 연동

- [x] 테스트 버튼용 고정 데이터 대신 실제 Run 상태로 요청 생성
- [x] 게임 종료 시 `POST /api/runs` 호출
- [x] 성공과 실패 결과를 플레이어가 확인할 수 있게 최소 표시
- [x] 네트워크 실패 시 게임이 멈추지 않도록 처리
- [x] 클리어 Run 1건과 사망 Run 1건을 실제 플레이로 저장
- [x] Web에서 두 기록의 순서와 내용 확인

### 첫 달 마감 점검

- [ ] Unity, Backend, Web 실행 절차가 문서와 일치하는지 확인
- [ ] 첫 달 동안 발견한 기술 부채를 별도 목록에 기록
- [ ] 실제 소요 시간을 기준으로 다음 4주 범위를 다시 산정
- [x] 장기 로드맵에서 현재 완료된 항목 표시

## 완료 조건

- 다음 달에 반영할 점: 에셋 직접 만들기는 너무 힘들다. 외주를 맡기거나 해야할 것 같다.

## 8. 일정이 밀릴 때의 축소 순서

일정이 예상보다 느릴 때는 다음 순서로 범위를 줄인다.

1. 연출, 사운드, 시각 효과를 제외한다.
2. 아이템과 랜덤 방을 제외한다.
3. 일반 방 수를 1개로 줄인다.
4. 보스 패턴을 1개로 고정한다.
5. Web은 텍스트 목록만 유지한다.

다음 항목은 축소하지 않는다.

- 사망과 클리어의 상태 구분
- Run 종료의 중복 처리 방지
- API 요청 검증과 오류 응답 확인
- DB 저장 후 Web에서 조회하는 관통 테스트

## 9. 작업 기록 규칙

각 작업 세션이 끝날 때 아래 내용을 짧게 남긴다. 별도 일지 문서나 커밋 메시지를 사용할 수 있다.

```text
날짜:
오늘 통과한 체크포인트:
막힌 문제:
다음에 바로 할 한 가지:
실제 작업 시간:
```

매주 마지막 날에는 체크되지 않은 항목을 무조건 다음 주로 복사하지 않는다. 해당 항목이 첫 달 최종 완료 조건에 필요한지 다시 판단하고, 필요하지 않다면 백로그로 이동한다.
