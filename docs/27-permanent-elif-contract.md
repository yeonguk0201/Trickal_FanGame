# 영구 엘리프 계약 설계 메모(Elif-0)

> 작성일: 2026-10-21  
> 계획: [26-seventh-month-plan.md](./26-seventh-month-plan.md) §5, D8  
> 관련 계약: [23-item-classification-contract.md](./23-item-classification-contract.md) §6(골드 enum), [07-api.md](./07-api.md), [06-database.md](./06-database.md)  
> 상태: **설계 확정, 구현 전.** 이 문서는 계약을 정할 뿐 Backend·Prisma·Unity 코드를 만들지 않는다. 구현은 §9의 조건부 조각에서 한다.

## 1. 요약

- 엘리프는 Run이 끝나도 남는 희귀 영구 화폐다. Run 화폐인 골드와 별개다.
- **획득**: 바닥에 떨어지는 골드 픽업이 생길 때 **7%** 확률로 골드 대신 엘리프 1개가 나온다. 아이시아의 지갑은 획득 시 한 번 추첨해
  엘리프 0~4개를 함께 준다. 3층 Run당 기대 획득량은 **약 0.5개**다.
- **사용**: 일반 상점(시스트)에서 **Run 중에** 상점 영구 업그레이드에 투자하고, 상점에 확률로 나오는 엘리프 가격 상품을 산다.
  업그레이드는 **산 즉시** 이번 Run부터 효과가 난다.
- **저장**: Run 도중 서버를 부르지 않는다. Run 시작 때 받은 잔액으로 쓰고, Run 결과 저장(`POST /api/runs`)에 획득·사용량을 함께 실어
  같은 트랜잭션에서 반영한다. `clientRunId` 재전송은 지금처럼 한 번만 반영된다.
- **저장되지 않는 Run**: 클리어·사망은 결과가 저장되므로 엘리프가 남는다. 포기·강제 종료는 결과가 저장되지 않으므로 그 Run의
  획득·사용·업그레이드가 모두 없던 일이 된다.

## 2. 사용자 결정(2026-10-21)

| 항목 | 결정 |
| ---- | ---- |
| 전환 확률 초기값 | 7%(시험 범위 5~10%의 중간, Balance-0에서 조정) |
| 사망·포기 | 클리어·사망은 유지, 포기는 소멸(포기 Run은 지금도 저장하지 않음) |
| 랜덤코인·네티의 지도 | 적용하지 않는다. 바닥 골드 픽업만 전환한다 |
| 업그레이드 구매 장소 | Run 중 일반 상점(시스트) |
| 업그레이드 적용 시점 | 즉시(이번 Run부터) |
| 엘리프 가격 환율 | 골드 가격 ÷ 10 올림 |
| 엘리프 가격 상품 등장 | 처음부터 확률로 등장(업그레이드 해금 아님) |
| 첫 업그레이드 | 상품 칸 추가, 상점 할인 |

2026-10-09 결정(26번 §5): 골드가 나오는 곳에서 5~10% 확률로 골드 대신 엘리프, 아이시아의 지갑은 획득 시 한 번 추첨
(0개 40%·1개 30%·2개 15%·3개 10%·4개 5%, 평균 1.1개). 영구 화폐가 있어도 열쇠·폭탄 없이 필수 보스 경로를 끝내는 원칙은 유지한다.

이 문서에서 **구현 기본값**이라고 적은 것은 사용자가 정하지 않은 세부를 제안한 값이다. 바꾸려면 알려 달라.

## 3. 획득

### 3.1 골드 픽업 전환

- 대상: 드롭 추첨에서 골드 후보가 뽑혀 **바닥 골드 픽업 1개가 생성되는 모든 지점**. 지금 코드 기준으로 다음과 같다.
  - 상자 내용물(`RoomChestSpawner`): 일반·황금·다이아몬드 상자의 골드.
  - 장애물 드롭(`DestructibleObstacle`): 짱돌(`obstacle-basic-drop-table`의 `elif` 항목), 황금돌, 마요의 열쇠꾸러미, 음식상자 3종, 시스트의 금고,
    마요의 수집품 상자, 셰이디의 랜덤박스의 골드.
  - 방 클리어 드롭(`RoomClearRewardSpawner`, `room-clear-drop-table`): 상자 전환 뒤에도 표가 쓰이는 곳이 있으면 포함한다.
- 대상 아님: 골드를 직접 지급하는 효과(아이시아의 지갑의 골드 100, 랜덤코인 `GainRandomGold`, 네티의 지도 `GainGold`), 상점 판매 소모품
  (골드는 팔지 않음), 멜룬카드가 복제한 골드 픽업(복제는 생성된 픽업을 그대로 복사하므로 다시 추첨하지 않음).
- 전환은 **픽업 1개마다 1번** 추첨한다. 시스트의 금고처럼 여러 개를 떨구면 골드가 뽑힌 칸마다 따로 추첨한다.
- 전환된 픽업은 엘리프 1개다. 골드는 주지 않는다(골드 **대신**).
- seed 재현(구현 기본값): 전환 추첨은 기존 드롭 난수열을 소비하지 않는 **별도 해시**(Run seed·방 ID·드롭원 ID·픽업 순번)로 한다.
  그래서 엘리프 도입 전과 같은 seed에서 어떤 칸에 골드가 나올지는 그대로이고, 그중 일부만 엘리프로 바뀐다.
  재방문·층 재구성은 기존 드롭 기록을 복원하므로 다시 추첨하지 않는다. 같은 seed의 결과가 바뀌므로 드롭 콘텐츠 버전을 올린다.

### 3.2 아이시아의 지갑

- 획득할 때 한 번만 추첨해 엘리프 0~4개를 바로 Run 획득량에 더한다(바닥 픽업 없음). 분포는 §2.
- 추첨은 Run seed와 아이템 인스턴스 ID로 재현한다. 지갑은 최대 1스택이고 같은 인스턴스를 다시 주워도 다시 추첨하지 않는다.
- 골드 100은 지금 규칙(99 상한, 초과분 버림) 그대로 준다.

### 3.3 Run당 기대 획득량(3층, 전투방 약 23개)

| 출처 | 골드 픽업 기대 수 | 엘리프(5%) | 엘리프(7%) | 엘리프(10%) |
| ---- | ----------------- | ---------- | ---------- | ----------- |
| 상자(클리어당 0.1304 × 23) | 약 3.0 | 0.15 | 0.21 | 0.30 |
| 장애물(짱돌 0.9%/개, 특수 장애물) | 약 1~2(추정) | 0.05~0.10 | 0.07~0.14 | 0.10~0.20 |
| 아이시아의 지갑(황금 특별 보상 약 0.4 × 지갑 약 1/2 × 1.1) | — | 약 0.2 | 약 0.2 | 약 0.2 |
| **합계** | | 약 0.4 | **약 0.5** | 약 0.6 |

- 장애물 골드 수는 장애물 수가 Layout마다 달라 추정치다. Balance-0의 층별 골드 획득 기록으로 실측해 이 표를 고친다.
- 9층 확장 구상(전투방 약 100)에서는 Run당 약 1.5~2개가 된다. 층을 늘릴 때 확률을 층 구간별로 나눌지 다시 본다.

## 4. 사용

### 4.1 엘리프 가격 상품

- 일반 상점과 골디 상점의 아티팩트 3칸을 만들 때, 상점마다 **25%** 확률(구현 기본값)로 그중 1칸이 엘리프 가격 상품이 된다.
  어느 칸인지도 상점 seed로 정한다. 같은 칸의 아이템 선택 규칙(풀·등급 가중치·보유 한도)은 그대로이고 가격만 바뀐다.
- 가격 = 골드 가격 ÷ 10 올림. 지금 가격표로 Common 1·Uncommon 2·Rare 2·Epic 3이다.
- 엘리프로만 살 수 있다(골드 결제 불가). 상점 할인 업그레이드는 엘리프 가격에 적용하지 않는다.
- 멤버십카드는 "진열된 미구매 상품 가격을 전부 0"이라는 기존 규칙대로 엘리프 가격 상품도 무료로 만든다(구현 기본값).
- 소모품 3칸에는 엘리프 가격을 붙이지 않는다.
- 판매 완료·무료 상태는 기존 `ShopStockState`에 그대로 보존한다. 칸이 엘리프 가격인지도 함께 보존한다.

### 4.2 상점 영구 업그레이드

일반 상점(시스트) 화면에서 산다. 3×3 화면 오른쪽 아래 `투자` 버튼으로 업그레이드 목록을 열고, 다음 단계 비용을 엘리프로 낸다
(화면 구성은 구현 기본값, UX-1과 함께 확정). 골디 상점에서는 팔지 않는다. 효과는 두 상점 모두에 적용한다.

| 안정 ID | 이름 | 단계 | 효과 | 단계별 비용(구현 기본값) |
| ------- | ---- | ---- | ---- | ------------------------ |
| `shop-upgrade-extra-slot` | 상품 칸 추가 | 3 | 단계마다 아랫줄 빈 칸 1칸에 아티팩트 상품 1개 추가(일반 상점은 기존 선택 보상 풀, 골디 상점은 Rare 이상) | 2 / 3 / 5 |
| `shop-upgrade-discount` | 상점 할인 | 3 | 골드 가격 10% / 20% / 30% 할인. `max(1, floor(가격 × (1 − 할인율)))` | 2 / 3 / 4 |

- 전 단계 합계 19개, Run당 0.5개 기준 약 38 Run이다. 엘리프 가격 상품과 경쟁하므로 비용은 Balance-0 뒤 다시 본다.
- 할인 예시: 아티팩트 10/15/20/25 → 1단계 9/13/18/22, 2단계 8/12/16/20, 3단계 7/10/14/17. 하트 3 → 2/2/2, 열쇠·폭탄 5 → 4/4/3.
- **즉시 적용**: 할인은 산 순간 지금 상점의 미구매 상품 가격부터 바뀐다. 상품 칸 추가는 산 순간 지금 상점 아랫줄에 새 칸이 생긴다.
  새 칸의 상품은 상점 seed와 칸 번호로만 정해(구현 기본값) 언제 업그레이드했는지와 관계없이 같은 상점에서 같은 결과가 나온다.
  이미 만들어진 칸의 상품은 바꾸지 않는다. 이후 이 Run에서 처음 만드는 상점에도 적용된다.
- 업그레이드 ID는 Item ID와 같은 안정 키로 다룬다. 의미를 바꾸거나 재사용하지 않고, 폐지할 때도 카탈로그에서 지우지 않는다.

### 4.3 Run 중 잔액과 동기화

Run 도중 서버를 부르지 않는다. 모든 계산은 Run 시작 때 받은 값과 이번 Run의 기록으로 한다.

```text
시작 잔액 S = 서버 elifBalance − 저장 대기 중인 이전 Run들의 elif.spent 합
쓸 수 있는 엘리프 = S + 이번 Run 획득 − 이번 Run 사용
```

- Run 시작 시 `GET /api/users/:nickname` 응답의 `meta.elifBalance`와 `meta.shopUpgrades`를 받는다(§6.2).
- 저장 대기 중인 이전 Run(`LocalPendingRunStorage`)이 있으면 그 Run의 **사용량과 업그레이드는 반영**하고 **획득량은 반영하지 않는다**.
  보수적으로 계산해 서버 저장 시 잔액이 모자라는 일을 줄인다. 대기 Run이 저장되면 다음 Run부터 획득량이 잔액에 들어온다.
- 이번 Run에서 주운 엘리프는 바로 쓸 수 있다.
- 시작 시 조회가 실패하면(구현 기본값): 이번 Run은 엘리프 사용(상품 구매·투자)을 막고, 업그레이드 효과는 마지막으로 성공한 조회 값을
  로컬 캐시에서 적용한다. 획득은 그대로 기록해 저장한다.
- Run 중 보유 상한은 두지 않는다(골드 99 상한과 별개). 서버 잔액 상한은 9999(구현 기본값)이며 넘는 획득분은 버린다.

## 5. 저장과 재전송

### 5.1 언제 반영되는가

| Run 종료 | 결과 저장 | 엘리프 |
| -------- | --------- | ------ |
| 클리어 | 저장 | 획득·사용·업그레이드 반영 |
| 사망 | 저장 | 획득·사용·업그레이드 반영 |
| 포기(`TryAbandonToHome`) | 저장 안 함(현행) | 모두 없던 일. 잔액·업그레이드 단계는 시작 전 그대로 |
| 강제 종료·크래시 | 저장 안 함 | 모두 없던 일 |
| 저장 실패 | 로컬 대기 후 재전송 | 저장 성공 시 반영. 대기 중에는 §4.3 규칙 |

- 포기로 엘리프 상품·업그레이드를 공짜로 얻는 일은 없다. 포기하면 그 Run에서 산 것도 함께 사라지기 때문이다. 이번 Run에서
  산 업그레이드를 다음 Run에 남기려면 결과가 저장되어야 한다는 점을 상점 투자 화면에 안내한다(구현 기본값).

### 5.2 Run 저장 요청 확장(`POST /api/runs`)

`CreateRunDto`에 선택 필드 `elif`를 더한다. 없으면 0으로 본다(과거 클라이언트·대기 요청 호환).

```json
{
  "elif": {
    "gained": 2,
    "spent": 4,
    "upgradePurchases": [
      { "upgradeId": "shop-upgrade-discount", "level": 1, "floor": 2, "order": 1 }
    ]
  }
}
```

- `gained`, `spent`: 0 이상 정수. `gained`는 Run당 상한(구현 기본값 50)을 넘으면 `400`으로 거부한다.
- `upgradePurchases`: 이번 Run에서 산 업그레이드 단계, `order`는 1부터 연속. 같은 업그레이드는 단계 순서대로만 올 수 있다.
- 개발 패널로 얻은 엘리프는 `gained`에 넣지 않는다(§7.2).

### 5.3 서버 처리(기존 Run 트랜잭션 안)

1. 기존과 같이 `clientRunId`로 저장된 Run을 찾는다. 있으면 fingerprint를 비교해 같으면 저장된 응답을 그대로 돌려주고, 다르면
   `409 RUN_IDEMPOTENCY_CONFLICT`. 엘리프는 다시 반영하지 않는다.
2. 업그레이드 검증: 서버 카탈로그(`SHOP_UPGRADE_CATALOG`)에 없는 ID·최대 단계 초과·단계 건너뛰기는 `400`. 각 구매의 비용은
   서버 카탈로그로 다시 계산하고, `spent`가 업그레이드 비용 합보다 작으면 `400`.
3. 서버에 이미 그 단계 이상이 있으면(다른 Run이 먼저 저장) 그 구매는 건너뛰고 비용을 `spent`에서 뺀다.
4. 새 잔액 = 기존 잔액 + `gained` − `spent`(상한 9999). 0보다 작아지면 0으로 두고 모자란 양을 `elifShortfall`에 기록한다.
   **잔액 부족으로 Run 저장을 실패시키지 않는다.** 전적·경험치가 사라지는 쪽이 더 나쁘기 때문이다. 정상 흐름(한 PC, 한 번에 한 Run)에서는
   §4.3의 보수적 계산 때문에 생기지 않고, 같은 프로필로 두 Run을 동시에 돌릴 때만 생긴다.
5. 업그레이드 단계를 올리고, 응답 스냅샷(`elifSnapshot`)을 Run에 저장한다. 재전송 시 이 스냅샷으로 같은 응답을 돌려준다
   (경험치의 `progressSnapshot`과 같은 방식).

응답 `data`에 `meta`를 더한다.

```json
{
  "meta": {
    "elifBalance": 7,
    "elifGained": 2,
    "elifSpent": 4,
    "shopUpgrades": [{ "upgradeId": "shop-upgrade-discount", "level": 1 }]
  }
}
```

### 5.4 fingerprint 호환

- `RUN_FINGERPRINT_FIELDS`에 `elif`를 더하되, **`elif`가 없거나 모두 0이면 지금과 같은 해시**가 나오게 한다. 로컬에 대기 중인 과거
  요청과 이미 저장된 Run의 재전송이 `409`로 바뀌지 않아야 한다. 이 경계를 Jest로 고정한다.

## 6. 계층별 영향

### 6.1 Prisma(구현 조각에서 마이그레이션)

| 대상 | 변경 |
| ---- | ---- |
| `User` | `elifBalance Int @default(0) @map("elif_balance")` |
| 새 `UserShopUpgrade` | `userId`·`upgradeId VarChar(64)`·`level Int`·생성/수정 시각, `@@unique([userId, upgradeId])`, User 삭제 시 Cascade |
| `Run` | `elifGained`·`elifSpent`·`elifShortfall Int @default(0)`, `elifSnapshot Json?` |
| 새 `RunUpgradePurchase` | `runId`·`upgradeId`·`level`·`floor`·`purchaseOrder`, `@@unique([runId, purchaseOrder])`, Run 삭제 시 Cascade |

- 업그레이드 카탈로그는 DB 테이블이 아니라 Backend 상수(`SHOP_UPGRADE_CATALOG`)로 둔다. seed는 바뀌지 않는다.
- 엘리프 가격 상품 구매는 따로 기록하지 않는다. 산 아이템은 지금처럼 `RunItem`에 남고, 엘리프 사용량은 `elifSpent`에 합쳐진다.
- 과거 Run은 기본값 0·스냅샷 없음으로 남는다. 과거 전적 표시는 바뀌지 않는다.

### 6.2 Backend

- `CreateRunDto`·검증·`runs.repository`의 트랜잭션·fingerprint·응답(§5).
- `GET /api/users/:nickname` 응답(07번 §9.4)에 `meta: { elifBalance, shopUpgrades }`를 더한다. 다른 사람 프로필에도 보여도 되는 정보다.
- `SHOP_UPGRADE_CATALOG`와 카탈로그 테스트. Unity 카탈로그와 ID·단계·비용 일치는 contract-drift-check 대상에 더한다.
- `07-api.md`·`06-database.md`를 함께 고친다.

### 6.3 Unity

- `RunResourceType`에 `Elif = 3`을 **뒤에 추가**한다(23번 §6). 값 0(골드)은 바꾸지 않는다.
- 새 픽업 Prefab은 **`PermanentElifPickup.prefab`**처럼 다른 이름으로 만든다. `ElifPickup.prefab`은 골드 픽업이다(경로·GUID 유지).
  새 드롭 항목 ID도 `permanent-elif`로 한다. 기존 드롭 표의 `elif`는 골드를 뜻하는 데이터 키다.
- 전환 추첨은 공용 도우미 하나(예: `ElifConversion`)로 모아 §3.1의 모든 생성 지점에서 쓴다.
- `RunProgress`에 이번 Run의 엘리프 획득·사용·업그레이드 구매 기록과 시작 잔액. 골드 99 상한·층 이탈 규칙은 적용하지 않는다.
- `ShopStockBuilder`·`ShopRoom`·상점 화면: 엘리프 가격 칸, 할인, 추가 칸, `투자` 화면.
- `RunDto`(Unity DTO)·`RunSession`의 요청 구성, `LocalPendingRunStorage`에서 대기 요청의 사용량·업그레이드 읽기.
- 사용자 프로필 조회 결과에서 `meta`를 받고, 조회 실패 대비 마지막 값 캐시.
- HUD: 우측 자원 영역에 엘리프(쓸 수 있는 양)를 둔다. UX-1이 같은 영역을 배치하므로 자리를 함께 잡는다.
- 개발 패널(§7.2).

### 6.4 Web

- 사용자 대시보드(`web/src/app/users/[nickname]/user-dashboard.tsx`)에 엘리프 잔액과 업그레이드 단계.
- Run 상세에 엘리프 획득·사용(0이면 숨김). `web/src/lib/meta-api-contract.ts` 타입.
- 랭킹·통계는 바꾸지 않는다.

## 7. 검증 기준(구현 조각용)

### 7.1 자동

- Backend Jest: 정상 반영, 재전송 시 1회만 반영·같은 응답, 다른 데이터 재전송 `409`, `elif` 없는 요청의 fingerprint 불변,
  업그레이드 단계 건너뛰기·없는 ID·비용 부족 `400`, 다른 Run이 먼저 올린 단계의 건너뛰기와 비용 차감, 잔액 0 미만 시 저장 성공과
  `elifShortfall`, `gained` 상한.
- Unity: 전환 확률 분포(대량 seed에서 7% 근처)·seed 재현·기존 골드 위치 불변, 재방문 재추첨 없음, 지갑 분포와 1회 추첨,
  랜덤코인·네티의 지도 미전환, 엘리프 가격 칸 25%·가격 환산, 할인 계산과 즉시 반영, 추가 칸의 seed 고정, 잔액 부족 시 구매 실패와
  미소비, 포기 시 요청 미생성, 대기 요청 반영 계산.
- contract-drift-check: 업그레이드 ID·단계·비용, `RunResourceType` 값.

### 7.2 개발 패널(`F1`)

- `— Elif —`: `+5 Elif (dev)`(Run 안에서만 쓰고 저장 요청의 `gained`에 넣지 않음), `Next gold drop → Elif`(다음 골드 픽업 1개 강제 전환),
  `Drop Elif pickup`, 시작 잔액·획득·사용·쓸 수 있는 양 표시, 업그레이드 단계 표시와 `Set upgrade level`(이번 Run 한정, 저장 안 함).
- 기존 `+10 Bomb/Key/Elif` 버튼의 `Elif`는 골드를 더한다. 같은 조각에서 표시를 `Gold`로 바꾼다.

### 7.3 수동

- 정상 Run에서 엘리프를 줍고 사망 → 다시 시작했을 때 잔액이 늘어 있는지, 포기 → 늘지 않았는지.
- 상점에서 투자 후 같은 상점 가격·칸이 바로 바뀌는지, 다음 Run에도 유지되는지. 저장 실패 → 재시도 뒤 한 번만 반영되는지.
- Web 사용자 화면의 잔액.

## 8. 바뀌지 않는 것

- 골드: 픽업 1개 = 골드 1, 99 상한, 상점 가격표, `ElifPickup.prefab`·드롭 ID `elif`.
- 열쇠·폭탄 없이 필수 보스 경로를 끝내는 원칙. 엘리프 상품·업그레이드는 모두 선택이다.
- 포기 Run을 저장하지 않는 현재 정책.
- Unity·Web은 DB에 직접 접근하지 않는다. 엘리프도 Backend API로만 읽고 쓴다.

## 10. 남은 결정(다음 계획으로 이관)

- 멜룬카드가 바닥 엘리프 픽업을 복제할 수 있는지. 구현 기본값은 **복제 대상에서 제외**(영구 화폐를 늘리는 경로를 막음).
- 마요의 수집품 상자·황금돌·시스트의 금고의 전용 엘리프 드롭(26번 §5). 지금은 §3.1의 공통 전환만 적용한다.
- 업그레이드 비용·엘리프 가격 상품 등장률 25%·전환 확률 7%의 조정(Balance-0 실측 뒤).
- 상점 업그레이드 이후 후보(시작 골드, 상점 리롤 등)와 상점 밖 사용처.
- 같은 프로필 동시 Run에서 생긴 `elifShortfall`을 그대로 둘지, 이후 획득에서 갚게 할지.
- 9층 확장 시 층 구간별 전환 확률.
