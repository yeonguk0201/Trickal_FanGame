## 1. 이 문서의 역할

첫째 달부터 셋째 달까지 Unity → Backend → Database → Web의 전체 흐름과 3층 Run, 스킬,
아티팩트, 메타 성장, 전적, 통계와 랭킹을 완성했다. 넷째 달에는 새로운 시스템의 수를 늘리기보다
현재 플레이에서 확인된 다음 문제를 해결한다.

1. 플레이에 필요한 HP, SP, 스킬, 아티팩트와 진행 정보가 충분히 보이지 않는다.
2. 게임 실행 직후 전투 화면이 노출되고 홈·설정·성장으로 이어지는 제품 흐름이 없다.
3. 방의 절대 크기와 전투 공간이 작고 모든 방의 체감이 비슷하다.
4. 현재 적 3종은 감지 거리 밖에서 쉽게 무력화되며 행동과 조합이 단순하다.
5. 층별 보스의 고유 패턴과 공략 과정이 아직 확정되지 않았다.
6. 아티팩트가 존재하지만 플레이어가 보상을 비교하고 선택하는 과정이 부족하다.

이번 달은 **화면 흐름과 전투 가독성 → 공간과 Encounter → 적 행동과 보스 → 선택 보상과
종합 플레이테스트** 순서로 진행한다. 정식 아트를 먼저 완성하지 않고 임시 UI와 기능성 에셋으로
규격과 재미를 검증한 뒤 교체한다.

## 2. 시작 시점의 확정 기반

### 완료된 게임 흐름

- 에르핀 1종으로 시작하는 3층 전체 Run
- 층당 6~8개의 seed 기반 격자형 방
- 시작방·일반 전투방·보물방·보스방
- 추적형·원거리형·돌진형 일반 적 3종
- 층별 보스와 최종 보스 진행
- 기본 공격, SP, 저학년 스킬과 고학년 스킬
- 활성 아티팩트 10종, 등급, 최대 스택과 시너지
- Run 종료 경험치와 스킬 포인트 기반 영구 성장
- Run 저장, Web 전적·통계·랭킹 연동

### 이번 달의 제품 방향

- 캐릭터 수는 에르핀 1종으로 유지한다.
- 16:9 화면 비율과 **현재 방 하나만 활성·노출하는 원칙**을 유지한다. 현재 방이 기준 화면보다
  작거나 같으면 카메라를 방 중앙에 고정하고, 더 큰 축에서만 플레이어를 제한 추적한다.
- 기준 UI 해상도는 `1920 × 1080`으로 한다.
- 게임용 계정이나 로그인 대신 한 PC의 **로컬 플레이어 프로필**을 사용한다.
- 타이틀·홈을 전투 Scene과 분리하고 게임 시작 전에는 전투 맵을 노출하지 않는다.
- 기존 `16 × 9` 방을 삭제하지 않고 더 큰 Room Profile과 Encounter를 추가해 비교한다.
- 새 일반 적을 추가하기 전에 기존 3종의 역할과 대응 방법을 완성한다.
- 정식 장식 에셋보다 플레이 정보와 공격을 읽게 해주는 기능성 에셋을 우선한다.

## 3. 넷째 달 최종 완료 조건

2026-12-07까지 다음 흐름을 한 게임 안에서 반복할 수 있어야 한다.

```text
EXE 실행
  → 타이틀 화면
  → 최초 사용자라면 닉네임 등록
  → 홈 화면
  → 캐릭터 선택
  → 서로 다른 크기와 Encounter의 방 진행
  → HUD를 보며 스킬과 아티팩트 상태 판단
  → 행동이 명확한 일반 적 3종과 전투
  → 층별 보스 전투
  → 아티팩트 후보 3개 중 1개 선택
  → 최종 클리어 또는 사망
  → 결과 확인
  → 홈 또는 캐릭터 선택
```

### 플레이 경험 완료 조건

- 사용자는 게임 실행부터 Run 시작까지 전투 Scene을 보지 않고 이동할 수 있다.
- 최초 사용자는 중복되지 않는 닉네임으로 로컬 플레이어 프로필을 만들 수 있다.
- 사용자는 전투 중 HP, SP, 스킬, 아티팩트, 방·층과 보스 상태를 확인할 수 있다.
- 기존 크기와 1.5배 크기 이상의 방이 같은 Run에서 서로 다른 전투 공간으로 느껴진다.
- 적은 방 전투가 시작되거나 피격된 뒤 감지 거리 밖에서 무력화되지 않는다.
- 추적형은 거리 관리, 원거리형은 파고들기, 돌진형은 회피라는 서로 다른 대응을 요구한다.
- 보물방과 보스 보상에서 후보를 비교하고 하나를 선택할 수 있다.
- 보스의 공격은 예고, 대응 방법과 공격 후 빈틈을 제공한다.
- 전체 Run을 여러 seed로 완료하며 심각한 진행 차단이나 중복 보상이 없다.

# 6. 13주차 — Frontend와 전투 UI

## 목표

게임 실행 직후 전투 화면이 노출되는 현재 구조를 타이틀·홈 중심의 제품 흐름으로 교체하고,
플레이어가 전투 판단에 필요한 정보를 확인할 수 있는 최소 HUD를 완성한다.

## 권장 진행 순서

```text
UI 규격 확정
  → Frontend Scene 분리
  → 타이틀과 Frontend 화면 상태 관리
  → 닉네임 등록 UI와 프로필 등록 계약
  → 홈 화면 골격
  → 로컬 프로필 재실행·오류 통합 검증
  → 스킬 강화와 설정
  → 캐릭터 선택
  → Game Scene 진입과 로컬 Run 초기화
  → 전투 HUD(HUD-1~7B)
  → Run 결과와 Frontend 복귀
  → 일시정지에서 홈 나가기와 같은 캐릭터 재시작(HUD-7C~7D)
  → 전체 흐름 통합 검증
  → 임시 에셋 교체 규격 확정
```

## 작업 조각과 진행 기준

13주차 작업은 아래 조각 단위로 구현하고 검증한다. 표의 순서는 시스템 의존성 순서이며,
앞 조각의 완료 조건을 만족한 뒤 다음 조각으로 이동한다. 서로 독립적인 화면 배치 작업은 먼저
진행할 수 있지만, 프로필·Run·설정 데이터를 임시 값으로 우회한 상태를 해당 조각의 완료로
처리하지 않는다.

#### Flow-5 결과 화면과 연출 기준

결과는 Game Scene 위의 `Esc`형 팝업으로 남기지 않는다. Run 종료 직후 전투 입력을 막고 짧은
전환을 거쳐 Frontend Scene의 **전체 화면 결과 상태**로 이동한다. 별도 Result Scene은 만들지 않되,
전투 화면과 HUD가 뒤에 비치지 않아 플레이어에게는 독립된 결과 화면으로 보여야 한다.

결과 화면의 목적은 많은 정보를 동시에 나열하는 것이 아니라, 짧은 호흡으로 보상을 연속 공개해
쾌감과 성취감을 전달하는 것이다. 왼쪽에는 선택 캐릭터와 말풍선을 계속 표시하고 클리어 시
의기양양한 반응, 사망 시 속상하거나 우는 반응을 사용한다. 오른쪽의 한 연출 영역은 아래 내용을
동시에 쌓지 않고 순서대로 교체한다.

```text
RUN CLEAR / RUN FAILED
  → 캐릭터 결과 반응과 짧은 대사
  → 도달 층·처치 수·플레이 시간과 사망 원인
  → 획득 경험치와 경험치 바 연속 충전
  → 레벨 변화 한 번 표시
  → 획득·보유 스킬 포인트
  → 획득 아티팩트 회고
  → 최종 요약과 다시 도전·홈으로
```

- 경험치 바는 시작 레벨의 현재 경험치부터 최종 경험치까지 실제 레벨 경계를 차례로 통과한다.
  여러 레벨이 오르면 경계를 넘을 때마다 짧은 빛·충격·효과음으로 `빰빰빰` 이어지게 하고, 첫
  구간 뒤에는 충전 속도를 높여 레벨 수만큼 긴 연출이 되지 않게 한다.
- 여러 레벨 상승 결과는 레벨마다 별도 화면을 반복하지 않는다. 모든 경험치 충전이 끝난 뒤
  `LEVEL UP!`과 `Lv. 1 → Lv. 10`처럼 시작·최종 레벨을 한 번만 크게 표시한다. 한 레벨만 오르면
  같은 형식으로 표시하고, 레벨이 오르지 않으면 이 단계를 생략한다.
- 경험치 연출은 Backend가 반환한 실제 획득 경험치와 최종 진행만 사용한다. 저장 실패 상태에서
  예상 성장 수치를 확정값처럼 연출하지 않고, 같은 `clientRunId`의 결과 저장 재시도를 우선한다.
- 확인 입력은 현재 숫자·게이지 연출을 즉시 끝내고, 추가 확인 입력은 남은 연출을 건너뛰어 최종
  요약으로 이동한다. 건너뛰어도 최종 레벨·경험치·스킬 포인트와 저장 결과는 정확히 남는다.
- `다시 도전`은 이전 Run을 완전히 정리한 뒤 캐릭터 선택으로 이동해 새 seed와 새 `clientRunId`로
  시작한다. `홈으로`도 같은 정리를 거쳐 홈 상태로 이동하며 결과 저장을 중복 호출하지 않는다.

  Flow-3 → Flow-4 → HUD-1~7B → Flow-5 → HUD-7C~7D·Setting-1C`의 전체 흐름을 마지막에

- Frontend는 프로필·설정·선택 상태를 표시하고 요청하지만 전투 상태를 소유하지 않는다. Game
  Scene의 `RunSession`은 한 Run의 상태를 소유하며, Backend Run 레코드는 종료 결과 저장 시 만든다.

# 7. 14주차 — Room Profile과 Encounter

## 목표

기존 방을 보존하면서 크기와 형태가 다른 검증된 Room Template을 seed 생성에 연결한다. 카메라는
모든 방을 한 화면에 맞추려고 축소하지 않고, 현재 방이 기준 화면보다 큰 축에서만 플레이어를
추적한다. 방 공간에 맞는 적 조합과 웨이브를 데이터로 구성해 방마다 다른 전투가 일어나게 한다.

## 방 크기 검증 기준

| 템플릿 후보 | 기준 방 대비 크기 | 카메라 이동 축 | 우선 용도 |
|---|---:|---|---|
| Small | 가로·세로 모두 1× 이하 | 없음, 방 중앙 고정 | 짧고 밀도 높은 전투 |
| Basic | 현재 `16 × 9` | 없음, 방 중앙 고정 | 기존 회귀 기준 |
| Wide | 가로 약 1.5×, 세로 1× 이하 | 가로만 추적 | 횡이동·저격 대응 |
| Tall | 가로 1× 이하, 세로 약 1.5× | 세로만 추적 | 종이동·웨이브 실험 |
| Large | 가로·세로 약 1.5× | 가로·세로 추적 | 복합 Encounter |
| Boss 후보 | 필요한 축 1.5~2× | 큰 축만 추적 | 보스·특수 전투 |

위 값은 시작 후보이며 카메라의 기준 확대율은 기존 방과 같은 전투 가독성을 우선한다. 방 전체를
보이게 하려고 Ortho Size를 방 크기만큼 키우지 않는다. 각 축에서 방의 카메라 이동 가능 길이가
0 이하면 방 중앙에 고정하고, 양수인 축만 플레이어 위치를 방별 경계 안으로 제한해 추적한다.

```text
cameraX = clamp(playerX, roomCameraMinX, roomCameraMaxX)  // 가로가 클 때만 범위가 생김
cameraY = clamp(playerY, roomCameraMinY, roomCameraMaxY)  // 세로가 클 때만 범위가 생김
```

따라서 가로로 긴 방은 세로 화면 구도가 흔들리지 않고 가로만 움직이며, 기본 방과 더 작은 방은
두 축 모두 고정된다. 14주차 첫 검증은 Basic·Small·Wide를 우선하고 Tall·Large·Boss는 같은 계약을
재사용해 순차 확장한다.

### Room 내부 생성 원칙과 14주차 범위

최종 Room 생성은 **절차적으로 만든 층 그래프에 수작업 Room Layout을 seed로 선택하는 방식**으로
구성한다. 벽·문·필수 통로와 전투 판단을 바꾸는 핵심 기둥은 Layout에 고정하고, 적·장애물을 방의
임의 좌표에 흩뿌리지 않는다. 후속 랜덤 장식·파괴물·SpawnPoint도 Layout에 미리 지정한 안전한 후보
슬롯에서만 선택하며 같은 seed와 콘텐츠 버전에서 재현되어야 한다.

14주차에는 이 구조의 기반만 검증한다.

1. 기존 Basic 방을 보존한 채 Room Profile·Template 계약을 만든다.
2. Small·Basic·Wide 수작업 Template과 축별 카메라 경계를 연결한다.
3. 문 방향과 방 크기가 호환되는 Template을 seed로 결정적으로 선택한다.
4. 각 Layout에 허용된 Encounter와 SpawnPoint 조합만 선택한다.
5. 마지막으로 파괴되지 않고 드롭이 없는 **고정 기둥 Layout 1종**을 추가해 이동, 투사체 사선,
   적 막힘과 출입구 안전 영역을 검증한다.

이 단계에서는 기둥 HP·파괴·확률 드롭, 열쇠·폭탄·파괴 가능한 벽·비밀방, 방 내부 장애물의 완전
절차적 배치를 구현하지 않는다. 추후 파괴물과 탐색 자원을 추가할 때도 고정 Layout 위의 제한된
후보 슬롯과 `RoomRunState` 상태 보존 계약을 확장해서 사용한다.

## 권장 진행 순서

```text
기존 Basic 방 회귀 기준 고정
  → Room Profile·Template 계약
  → 축별 카메라 계산
  → Small·Basic·Wide 수작업 Template
  → 문·크기 호환과 seed 기반 선택
  → 방 전환·안전 진입·미니맵 통합
  → Encounter 데이터 계약과 안전거리
  → 혼합 Encounter
  → 웨이브·재방문 상태
  → Tall·Large와 보스방 초안
  → 고정 기둥 Layout과 적 막힘 검증
  → 3층 전체 흐름 통합 검증
```

Room 내부 콘텐츠부터 만들지 않고 기존 방의 불변조건과 데이터 계약을 먼저 고정한다. 카메라와
Template 선택은 적 배치와 독립적으로 검증하고, Encounter는 사용할 수 있는 Room Profile과
SpawnPoint가 준비된 뒤 연결한다. 기둥 Layout은 현재 적의 직선 이동·돌진·투사체 충돌이 실제로
막히는지 함께 확인해야 하므로 기본 Encounter와 재방문 상태가 안정된 뒤 진행한다.

### Room-1 Room Profile·Template 계약 — 2026-09-15

Profile·Room Prefab·허용 RoomType, 4방향 문 슬롯·안전 진입점과 SpawnPoint를 묶으며 실제 Prefab
좌표와 계약 값이 다르면 검증을 거부한다.

기존 Basic 방은 `basic` Profile과 `basic-standard` Template 에셋으로 표현했다. Setup을 두 번
실행해 두 에셋 GUID가 유지되는지 확인했고, 빈 ID·중복 profile/template ID·누락 Profile을 실패
경로로 검증했다. 기존 `room-grid-base.prefab`과 Game Scene GUID는 유지됐으며 Room-0의 고정 seed,
이동·전투·재방문 회귀도 함께 통과했다. Profile과 Template에는 `RoomRunState`를 저장하지 않는다.

### Room-2 축별 카메라 경계 공통 규칙 — 2026-09-15

`RoomCameraFraming`은 방 내부 크기, Orthographic Size와 실제 카메라 종횡비로 뷰포트 크기를 구하고,
각 축의 이동 가능 길이를 `max(0, roomSize - viewportSize)`로 계산한다. 길이가 0인 축은 방 중앙에
고정하고 양수인 축만 플레이어 위치를 허용 중심 범위로 제한하므로 Small·Basic은 고정, Wide는
가로, Tall은 세로, Large는 양축 추적이라는 같은 규칙을 사용한다. `RoomProfile`의 16:9 제작 경계도
이 계산 결과와 일치해야 유효하다.

`RoomCameraController`는 Profile 적용 시 기존 무제한 `CameraFollow`를 비활성화하고 공통 계산 결과를
사용한다. 방 진입 순간 플레이어 위치를 새 방의 유효 범위로 즉시 제한한 뒤 같은 범위 안에서만
보간하므로 이전 방의 카메라 위치를 끌고 오지 않는다. `Week14Room2Verification`은 Small·Basic·
Wide·Tall·Large, 양끝 극단 좌표, 잘못된 크기·확대율·종횡비, 방 로컬 좌표의 런타임 적용과 Room-0~1
회귀를 Unity 6000.3.22f1 배치 실행으로 검증했다.

### Room-3 Small·Basic·Wide 수작업 Template — 2026-09-15

기존 Basic `16 × 9`와 `room-grid-base.prefab`은 수정하지 않고, Small `12 × 6.75`와 Wide `24 × 9`
Profile·Prefab·Template을 별도 안정 ID로 추가했다. Small과 Wide는 이 단계에서 일반 전투방만
허용하며, 네 방향 벽·문 슬롯·안전 진입점, 중앙 Encounter trigger와 수작업 SpawnPoint 3개를 가진다.
Small은 중앙 고정, Wide는 Room-2 규칙에 따라 가로만 추적한다.

Encounter trigger는 플레이어의 방 진입을 감지해야 하므로 출입구 통로와 공간상 겹칠 수 있다.
안전 규칙의 실제 금지 대상은 적 SpawnPoint와 후속 장애물이며, 문 슬롯에서 안전 진입점까지 파생한
필수 통로 안에 SpawnPoint가 있으면 Template 검증이 실패한다. 이는 기존 Basic의 회귀값을 보존하면서
입장 직후 적 생성과 통로 차단을 방지하는 계약이다.

`Week14Room3Setup`을 두 번 실행해 새 Profile·Template·Prefab 여섯 에셋의 GUID가 유지되고 기존 Basic
Prefab과 Game Scene GUID가 바뀌지 않는지 확인했다. `Week14Room3Verification`은 세 크기의 벽·문 개구부,
안전 진입점, Encounter·SpawnPoint, 카메라 모드와 필수 통로 침범 실패 경로를 검사한 뒤 Room-0~2
회귀를 함께 통과했다.

### Room-4 호환 필터와 seed 기반 Template 선택 — 2026-09-15

`FloorGenerator`는 콘텐츠 버전과 Small·Basic·Wide Template 카탈로그를 보유하고 논리 방 그래프를
완성한 뒤 각 `GeneratedRoomNode`에 안정 `templateId`를 배정한다. `RoomTemplateSelector`는 후보를
ID 순으로 정렬해 에셋 배열 순서의 영향을 제거하고, 방의 `contentSeed`와 콘텐츠 버전에서 선택
시작점을 파생한다. 후보는 RoomType과 모든 연결 방향을 지원해야 한다.

크기 호환은 기존 `20 × 13` grid 좌표를 월드 중심으로 변환한 뒤 Profile 내부 크기의 AABB로 판정한다.
방 번호 순서로 이미 배정된 모든 방과 겹치지 않는 첫 후보를 선택하므로 가로 인접 Wide–Wide는
제외되고 Small이나 Basic으로 결정적으로 폴백한다. Wide–Small과 세로 인접 Wide–Wide는 현재 간격에
들어가므로 허용한다. 이번 규격에서는 간격 자체를 바꿀 필요가 없어 Room-0의 `20 × 13`을 유지했다.

고정 seed의 기존 좌표·역할·RoomDefinition·연결 서명은 그대로 유지됐다. 같은 seed·버전 반복과
카탈로그 역순에서 동일한 Template 서명을 확인했고, 128개 seed에서 세 일반방 Template이 모두
선택되며 배치 겹침이 없음을 검증했다. 콘텐츠 버전 변경은 별도 결정 결과를 만들고 Reward/Boss
호환 Template이 없는 카탈로그는 명시적으로 실패한다. Room-0~3 회귀도 함께 통과했다.

### Room-5 실제 Prefab 전환과 화면 상태 연결 — 2026-09-15

`RoomGraphAssembler`는 각 `GeneratedRoomNode`에 선택된 Template의 실제 Room Prefab을 인스턴스화하고
해당 Profile을 런타임 `RoomNode`에 적용한다. 따라서 Small·Basic·Wide의 벽, 문, Encounter 영역과
SpawnPoint가 논리 선택 결과와 일치한다. 연결문은 목적지의 반대 방향 슬롯에 있는 안전 진입점을
계속 사용하며, 전환 실패 시 방 표시와 플레이어 위치를 원래 상태로 되돌린다.

`RoomGraphController`는 시작방과 이후 전환 모두에서 현재 Profile을 `RoomCameraController`에 전달한다.
카메라는 플레이어를 안전 진입점에 배치한 뒤 새 방의 유효 경계 안으로 즉시 제한되므로 이전 방
중심이나 벽 바깥을 비추지 않는다. `RunProgress`의 방 변경 이벤트는 기존 HUD 흐름을 유지하고,
미니맵 마커는 Profile의 실루엣 경계 비율을 사용해 Small·Basic·Wide 크기 차이를 표시한다.

Unity 6000.3.22f1 배치 검증은 세 Prefab이 함께 선택되는 seed에서 실제 인스턴스의 Profile과
Encounter 크기를 확인하고, 서로 다른 크기의 인접 방을 왕복하며 반대편 안전 진입점, 현재 방 하나만
활성화, 방문 상태 유지, 카메라 크기·중심 경계, `RunProgress`와 현재 미니맵 마커 갱신을 검사했다.
Setup 재실행과 Room-0~4 회귀를 포함해 종료 코드 0으로 통과했다.

첫 수동 검증에서 Wide 카메라 추적 중 캐릭터가 떨려 보이는 현상이 확인됐다. 플레이어 이동은
`FixedUpdate` 물리 프레임에 적용되지만 카메라는 렌더 프레임의 `LateUpdate`에서 위치를 읽는 반면,
플레이어 `Rigidbody2D` 보간이 꺼져 있던 것이 원인이었다. Room-5 Setup에서 `Interpolate`를 명시해
두 프레임 사이의 표시 위치를 보간하도록 수정했다. 이후 사용자가 Small·Basic·Wide를 다시 플레이해
Wide 카메라와 캐릭터 이동이 자연스러워졌고 다른 방 전환에도 이상이 없음을 확인했다.

### Encounter-1 정적 계약과 seed 선택 — 2026-09-15

`EncounterDefinition`은 안정 `encounterId`, 허용 Room Profile·층 범위, 적 역할·수, `spawn-01` 형식의
SpawnPoint 또는 `all` SpawnGroup, 플레이어·출입구 안전거리, 순서가 있는 웨이브 시작·종료 조건과
방 클리어 조건을 소유한다. 적 Prefab과 실제 좌표는 소유하지 않으며, 좌표는 선택된
`RoomTemplateDefinition`의 SpawnPoint 계약에서 해석한다.

`EncounterSelector`는 Room Template 선택이 끝난 일반 전투방만 대상으로 호환 후보를 안정 ID 순으로
정렬하고, 방의 content seed와 Encounter 콘텐츠 버전에서 결과를 결정한다. 선택 결과는
`GeneratedRoomNode`에 저장된다. 빈·중복 ID, 지원하지 않는 Profile·층, 존재하지 않는 SpawnPoint,
한 웨이브의 지점 중복 사용, 플레이어 안전 진입점 또는 문 슬롯과 너무 가까운 배치는 명시적으로
거부한다.

첫 계약 에셋은 기존 세 적 역할을 각각 한 마리씩 배치하는 `solo-chaser`, `solo-ranged`,
`solo-charging`이며 Small·Basic·Wide와 1~3층을 허용한다. 실제 적 Prefab 생성과 혼합 조합은
Encounter-2에서 연결하고, 재방문·보상 단일 지급은 Encounter-3에서 연결한다.

Unity 6000.3.22f1 배치 검증은 Setup 재실행 시 Scene·에셋 GUID 유지, 같은 seed·버전과 카탈로그
역순에서 같은 선택, 128개 seed에서 세 정의 선택, Profile·층·SpawnPoint·안전거리·중복 ID 실패
경로와 Room-0~5 회귀를 확인했고 종료 코드 0으로 통과했다.

### Encounter-2 혼합 조합과 실제 적 Prefab 연결 — 2026-09-15

Encounter가 적 Prefab을 직접 소유하지 않는 경계를 유지하기 위해 `EncounterEnemyRoster`가 추적형·
원거리형·돌진형 역할을 기존 검증 Prefab에 매핑한다. `RoomGraphAssembler`는 생성 노드에 선택된
Encounter의 첫 웨이브를 해석해 해당 역할 Prefab과 Template SpawnPoint의 일부만 `RoomController`에
전달한다. 두 번째 웨이브 이후의 진행 상태는 Encounter-3에서 연결한다.

첫 혼합 세트는 `pressure-chaser-ranged`, `lane-charging-ranged`, `crossfire-ranged`다. 추적형은
안전 후보 중 방 중심에 가까운 지점을, 원거리형·돌진형은 바깥 지점을 우선한다. `all` SpawnGroup은
현재 방에 실제로 연결된 문만 대상으로 플레이어 안전 진입점 1.5 유닛, 문 슬롯 2 유닛 거리를
확보하고 이미 사용한 지점을 제외한다. 따라서 같은 Encounter라도 Small·Basic·Wide의 좌표와 실제
연결 방향에 맞춰 안전한 위치가 결정되며, 필요한 수를 배치할 수 없는 다방향 원거리 조합은 해당
방의 후보에서 제외된다.

Unity 6000.3.22f1 배치 검증은 Setup 재실행 GUID, 역할 로스터의 Prefab·행동 컴포넌트, 256 seed에서
세 조합 선택과 활성 출입구 안전거리, SpawnPoint 중복 금지, 역할별 실제 Prefab 인스턴스 생성,
누락·중복 역할 실패 경로와 Room-0~5 회귀를 확인했고 종료 코드 0으로 통과했다. 입장 직후 피격,
돌진 회피 공간과 조합별 대응의 체감은 Play Mode 수동 검증 후 조각을 완료 처리한다.

사용자가 Play Mode에서 세 혼합 조합을 확인했으며 입장 즉시 피격, 회피 불가, 출입구 생성·막힘과
전멸 후 문 해제에 문제가 없음을 확인했다. 이에 따라 Encounter-2를 완료 처리한다. 적 개별 이동·
공격 패턴의 확장과 밸런스 조정은 15주차 범위로 유지하고, Encounter-2에서는 방 진행을 막는 조합
결함이 발견될 때만 최소 수정한다.

### Encounter-3 2웨이브·클리어 보상·재방문 상태 — 2026-09-16

2~3층 후보 `reinforcement-pressure`는 1웨이브의 추적형+원거리형을 모두 처치한 뒤에만 2웨이브의
돌진형+원거리형을 생성한다. `RoomController`는 각 웨이브의 필수 적을 개별 등록하고 마지막 적의
사망 이벤트에서만 완료 수를 전진시키므로 부분 전멸, 중복 사망 이벤트와 중복 시작으로 다음
웨이브가 앞당겨지지 않는다.

`RoomRunState`는 완료 웨이브 수와 클리어 보상 지급 여부를 Run 수명 동안 보존한다. 방이 다시
구성되면 첫 미완료 웨이브부터 이어지고, 이미 클리어된 방은 적을 생성하지 않는다. 일반 전투방의
클리어 보상은 기존 `SPPickup` 1개이며 생성 성공과 동시에 지급 상태를 기록한다. 따라서 같은 방
컨트롤러의 재진입과 Scene 인스턴스 재구성 모두에서 보상이 중복 생성되지 않는다.

Unity 6000.3.22f1 배치 검증은 256 seed의 2~3층 선택과 두 웨이브별 SpawnPoint 계약, 웨이브마다
필수 적 1마리만 남은 경계, 웨이브 시작·종료 단일성, 1웨이브 완료 상태 복원, 전체 클리어 후
재방문·재구성 시 적·SP 보상 중복 방지, Setup 재실행 GUID와 Room-0~5 회귀를 확인했고 종료 코드
0으로 통과했다.

### Room-6 Tall·Large와 층별 보스 Room Profile 초안 — 2026-09-16

일반 전투방에 Tall `16 × 13.5`와 Large `24 × 13.5` Profile·Prefab·Template을 추가했다. Tall은
세로축만, Large는 가로·세로축을 모두 추적하며 기존 Orthographic Size `5.25`, 네 방향 문,
안전 진입점, Encounter 영역과 SpawnPoint 3개 계약을 그대로 사용한다. 기존 Encounter 네 종도
Tall·Large를 허용해 실제 웨이브를 해석할 수 있다.

보스 공간 후보는 `boss-floor-1-wide(24 × 9)`, `boss-floor-2-tall(16 × 13.5)`,
`boss-floor-3-large(24 × 13.5)`로 분리했다. Profile·Template·Prefab은 층별 안정 ID를 가지며,
Template의 최소·최대 층 계약으로 다른 층에 선택되지 않는다. 현재 보스 행동과 Prefab 역할은
바꾸지 않고 공간·카메라·진입점·전투 영역 후보만 확정한다. 확장 후보가 이미 배정된 인접 방과
겹치면 기존 Basic 보스방으로 결정적으로 폴백한다.

기존 `20 × 13` 격자 간격은 유지한다. Tall–Tall 세로 인접, Large–Large와 Wide–Large 가로 인접처럼
겹치는 조합은 AABB 검사에서 제외하고 Small·Basic 등 호환 후보로 폴백한다. Unity 6000.3.22f1
배치 검증은 512 seed의 결정성, Tall·Large와 세 층 보스 후보 선택, 잘못된 층 범위 거부, 모든 방의
비겹침, Setup 재실행 GUID, Tall·Large Encounter 해석과 Encounter-3·Room-0~5 회귀를 확인했고 종료
코드 0으로 통과했다.

### Room-7 고정 기둥 Layout과 호환 Encounter — 2026-09-16

`large-central-pillar`는 Large `24 × 13.5` Profile을 재사용하고 중앙에 `3 × 3` 고정 기둥 하나를
둔 수작업 Template이다. 기둥은 안정 장애물 ID `central-pillar`, solid Collider와 `Environment`
레이어만 사용하며 HP, 파괴 동작, 드롭 소스와 이동 Rigidbody를 갖지 않는다. 네 출입구의 안전
진입점과 반대편 진입점 사이에는 플레이어 반경을 포함해 상하 또는 좌우 우회 경로가 남는다.

`pillar-crossfire`는 Large Profile 전용으로 추적형·원거리형·돌진형을 서로 다른 세 SpawnPoint에
배치한다. 현재 추적형은 새 길찾기를 추가하지 않고 기존 직선 이동과 Rigidbody 충돌 규칙을
유지한다. 따라서 기둥에 막힐 수 있지만 플레이어가 네 방향 통로로 우회해 전투를 끝낼 수 있어
Room 클리어를 막지 않는다. 장애물 자동 우회와 막힘 후 재탐색은 15주차 적 이동 계약에서 별도로
결정한다.

Unity 6000.3.22f1 배치 검증은 Setup 2회 실행의 에셋·GUID 안정성, 1,024 seed 안의 Layout/Encounter
동시 선택, 네 방향 필수 통로 비겹침과 반대편 안전 진입점까지의 우회 경로, 플레이어 크기 이동
sweep, 플레이어·적 투사체 사선 차단, 추적형 Rigidbody 충돌 예상과 돌진형 즉시 정지·회복 전환,
Room-0~6 및 Encounter-3 회귀를 확인했고 종료 코드 0으로 통과했다. 수동 검증 없이 완료 조건을
관찰 가능한 자동 검사로 충족했다.

### Room-8 예약 검증 — 이종 크기 좌우문 전환 잔상 — 2026-09-16

사용자 Play Mode 녹화에서 가로로 긴 방의 끝에 있는 좌·우 문을 통해 Basic 또는 Small 방으로
전환할 때, 두 방의 문이 화면상 바로 맞닿지 않는 조합에서 이전 방 화면 일부가 사각형 잔상처럼
남는 현상이 확인됐다. Small과 Basic 사이의 전환에서는 같은 현상이 관찰되지 않았다. 현재 증거만으로
이전 Room 비활성화 시점, 카메라 스냅·보간 순서, 렌더 버퍼 갱신 중 어느 것이 원인인지는 확정하지
않고 Room-8 종합 검증에서 조사한다.

Room-8에서는 Wide·Large에서 Basic·Small로 향하는 좌·우 문 전환과 그 역방향을 모두 재현한다.
특히 카메라가 긴 방의 가로 추적 경계 끝에 도달한 상태에서 전환 직후 첫 렌더 프레임과 보간 완료
후를 나눠 확인한다. 완료 조건은 현재 Room 하나만 활성화되고, 카메라 중심이 첫 프레임부터 목적지
Profile 경계 안에 있으며, 방 사이의 빈 공간이나 이전 Room 화면이 잔상으로 남지 않는 것이다.
활성 Room·카메라 경계는 자동 검증하고 실제 렌더 잔상은 Play Mode 녹화로 수동 확인한다.

Basic 방에 임시 적용한 통이미지는 벽 한 칸 정도 더 크게 보여도 될 여지가 있지만, 이는 고정형
배경의 배율 문제로 분류한다. 정식 타일·벽 조립 단계에서 크기를 맞추며 Room-8 잔상 원인과 섞어
수정하지 않는다.

### Room-8 3층 Run 종합 자동 검증 — 2026-09-16

`Week14Room8Verification`은 256개 seed마다 3층·층당 6~8방, 시작방·보스방 단일성, 같은 seed의
Template·Encounter·연결 결정성을 다시 생성해 비교한다. Small·Basic·Wide·Tall·Large, 중앙 기둥과
층별 보스 Template 아홉 종 및 Encounter 다섯 종이 실제 후보로 선택됐고, 모든 웨이브가 활성 문을
기준으로 서로 다른 안전 SpawnPoint에 해석되는지 확인했다.

실제 런타임 조립에서는 가로 추적 끝에 카메라를 둔 Wide/Large에서 Basic/Small로 향하는 좌·우 연결과
그 역방향을 재현했다. 전환 직후 목적지 하나만 활성이고 플레이어는 반대편 안전 진입점에 있으며,
카메라는 보간 전 첫 프레임부터 목적지 Profile 경계에 제한됨을 확인했다. 카메라가 이전 프레임을
보존하지 않도록 `SolidColor`로 매 프레임 뷰포트를 지우는 설정도 함께 고정했다.

2웨이브 방은 1웨이브 완료 상태에서 재구성해 2웨이브만 시작하고, 필수 적 전멸 뒤 클리어와 SP 보상
1회를 기록했다. 다른 층을 불러온 뒤 돌아와도 완료 웨이브·클리어·보상 상태가 유지되고 적이나 보상이
다시 생성되지 않았다. Unity 6000.3.22f1 배치 실행은 Room-0~7 전체 회귀를 포함해 종료 코드 0으로
통과했다.

최종 수동 확인은 `FrontendScene`에서 Run을 시작해 Wide 또는 Large 방의 좌·우 카메라 끝까지 이동한
뒤 Basic/Small/Tall 방으로 왕복하는 방식으로 수행했다. 전환 직후와 카메라가 멈춘 뒤 모두 이전 방
사각형, 방 사이 빈 공간 또는 비활성 방이 보이지 않아야 한다. 수정 후 사용자가 같은 경로에서 잔상이
사라졌음을 확인해 Room-8을 완료 처리했다.

사용자 재검증에서 세로 문은 정상이지만 Wide/Large의 화면 끝 가로 문에서 Basic/Small/Tall의 가로
문으로 이동할 때 넘어온 쪽 화면 끝에 이전 프레임이 남는 현상이 다시 확인됐다. 목적지 방이 카메라
가로 뷰포트보다 좁으면 새로 드러나는 옆 여백이 생긴다. 가로 격자 간격 `20`에서는 목적지 카메라
반폭 약 `9.33`의 넘어온 쪽 화면과 이전 Wide/Large 반폭 `12`의 월드 영역이 약 `1.33` 겹치지만,
세로 격자 간격 `13`의 전환 후 카메라는 이전 Tall/Large 영역을 벗어난다. 이 차이가 가로 화면 끝
문에서만 현상이 재현되는 공간 조건이다.

`RoomCameraController`는 초기화와 모든 방 표시 시 `SolidColor`와 배경 알파 `1`을 강제하며,
Room-5 Setup도 같은 값을 Game Scene에 직렬화한다. Room-8 검증은 불투명 클리어가 아니면 실패하도록
강화했다. 그러나 이 변경 뒤에도 같은 현상이 남아 단순 투명 클리어만의 문제는 아닌 것으로 확인됐다.
URP 히스토리 초기화도 사용자 재검증에서 효과가 없어 제거했다. 모든 Room Template의 Renderer가
실제 비활성화되는 `RoomNode.ContentRoot` 아래에 있는 검사는 유지한다.

**확인된 원인:** 첨부 GIF에서 전환 직후 흰 플레이어 사각형이 새 화면 가장자리에 잠깐 보였다.
`Week14Room8PlayVerification`으로 실제 문 트리거·물리 보간을 실행하니 Wide → Basic 첫 프레임의
물리 좌표는 `x=14.15`(목적지 안전 진입점), 표시 Transform은 `x=10.95`(이전 방)로 3.2유닛
어긋났다. 카메라가 이미 목적지로 옮겨진 상태에서 보간된 플레이어만 이전 위치에 그려지는 문제다.
이전 Wide/Large 위치는 새 카메라 가장자리 안에 들어오지만, Basic 출발이나 세로 전환의 이전
플레이어 위치는 대개 새 카메라 밖이므로 보이지 않았다. 방 영역 중첩 자체가 렌더 잔상의 원인은 아니다.

`RoomGraphController.MovePlayer`는 순간이동 때 보간을 잠시 해제하고 Rigidbody와 Transform 위치를
함께 변경한 후 원래 보간 모드를 복원한다. 같은 테스트가 수정 전 첫 전환에서 실패하고 수정 후
Wide/Large ↔ Basic/Small/Tall, 좌·우, 왕복 24개 전환에서 첫 5프레임 표시·물리 위치 일치 검사를
통과했다. 기존 Edit Mode 검사는 물리 위치만 검사해 이 문제를 놓쳤으므로 Play Mode 검증을 별도로
유지한다. 최종 사용자 Game View 재확인도 통과했으므로 이 문제의 완료 근거는 자동 24회 전환 검증과
실제 화면 검증을 함께 사용한다.

- [x] 층 상승은 HP와 개체 수 증가만이 아니라 역할 조합과 웨이브 복잡도로 표현한다. (2~3층 전용 2웨이브 Encounter 선택 검증, 2026-09-16)
- [ ] 좁은 방과 대형 방에서 같은 Encounter의 난이도가 달라지는지 비교한다.
- [ ] 롱레인지 저격형은 대형 방 Encounter에 우선 배치하고 기존 방에서의 사거리 처리를 정한다.

> 선택되며 방 전환, 재방문, 전멸 감지와 클리어 보상이 정상 동작한다.

# 8. 15주차 — 일반 적 3종과 보스 전투

## 목표

감지 거리 밖에서 적을 일방적으로 공격하는 문제를 제거하고 추적형·원거리형·돌진형이 서로
다른 이동과 공격 대응을 요구하게 한다. 층별 보스는 원작 보스 선정 후 상세 패턴을 확정한다.

## 공통 적 인식 계약

```text
대기
  → 방 전투 시작 또는 피격
경계
  → 플레이어가 멀어져도 추적·공격 유지
  → 방 클리어, 플레이어 사망 또는 방 비활성화 시 종료
```

- 감지 범위는 전투 전 활성화나 행동 시작 조건으로 사용할 수 있다.
- 한 번 경계한 적은 같은 전투 중 단순히 감지 범위를 벗어났다는 이유로 대기 상태로 돌아가지 않는다.
- 방 전투가 시작되면 해당 Encounter의 모든 적을 경계 상태로 만드는 것을 기본값으로 한다.
- 피격된 적은 공격 출처를 기준으로 즉시 플레이어를 인식한다.

## 적 3종의 대응 축

| 적 | 위협 방식 | 플레이어의 대응 |
|---|---|---|
| 추적형 | 붙어서 압박하고 근접 공격 | 거리 관리 |
| 원거리형의 저격형 변형 | 멀리서 멈춰 저격 | 파고들기 |
| 돌진형 | 방향을 고정한 직선 돌진 | 옆으로 회피 |

세 적이 모두 거리를 벌리는 대응만 요구하면 조합을 섞어도 플레이가 비슷해진다. 저격형 변형이
접근을 요구하는 축을 맡아 추적형·돌진형과 반대 방향의 압박을 만든다.

저격형은 기존 원거리형을 보존한 채 변형으로 추가한다. 이번 달 원거리 대응 축은 저격형으로
검증하며, 기존 원거리형을 대체할지는 플레이테스트 후 결정한다.

## 피해 모델 계약

- 원거리형과 돌진형은 접촉만으로 피해를 주지 않고 공격 동작 구간에서만 피해를 준다.
- 추적형은 접촉 피해와 예고 있는 근접 공격을 함께 가지며, 둘 다 해당 적의 공격력에 맞는 피해를 준다.
- 추적형의 접촉 피해는 근접 공격의 예고·회복 중에도 유지한다. 회복은 공격 동작과 추격의 빈틈이며 몸에 닿아도 안전한 시간은 아니다.
- 접촉 피해와 공격 피해는 플레이어의 같은 무적 시간을 공유하며 한 번에 두 번 적용되지 않는다.
- 새 공격을 추가할 때 접촉 피해를 함께 두려면 무적 시간 공유 여부를 먼저 확인한다.

## 필수 작업

### 공통 행동과 가독성

- [ ] 경계 상태 계약을 세 컨트롤러에 각각 구현하지 않고 공유 컴포넌트 하나로 제공한다.
- [ ] 방 전투 시작, 피격, 플레이어 사망과 방 비활성화에 맞춰 경계 상태를 전환한다.
- [ ] 먼 거리에서 공격하는 플레이어를 감지하지 못해 멈춰 있는 악용 경로를 제거한다.
- [ ] 넉백·사망·공격 예고 중의 이동 금지를 하나의 판정으로 통합하고 각 컨트롤러가 이를 참조한다.
- [ ] 세 컨트롤러에 중복된 대상 탐색과 행동 억제 로직을 공유 계약으로 정리한다.
- [ ] 플레이어의 공통 피격 무적 시간을 구현해 접촉·근접 공격·투사체·돌진의 중복 피해를 차단하고, 고학년 스킬 무적과 서로 해제하지 않게 한다.
- [ ] 공격 예고, 실제 위험 구간과 공격 후 빈틈을 색상 외의 형태·동작으로도 구분한다.
- [ ] 경직·넉백·사망·방 전환 중 진행 중인 공격이 올바르게 취소되는지 확인한다.
- [ ] 적이 방 경계 밖으로 이탈하지 않는지 회귀 확인한다. 벽 콜라이더로 이미 차단되어 있으므로
  신규 구현이 아니라 확인 항목으로 다룬다.

### 추적형

- [ ] 자체 공격 범위를 두고 플레이어가 그 안에 들어오면 근접 공격을 시작한다.
- [ ] 근접 공격 전에 짧고 읽을 수 있는 예고를 제공하고 예고 중에는 이동을 멈춘다.
- [ ] 근접 공격 판정은 공격 동작 구간에서만 활성화한다. 접촉 피해 판정은 별도로 유지한다.
- [ ] 공격 후 플레이어가 반격하거나 거리를 벌릴 수 있는 빈틈을 제공한다.
- [ ] 접촉 피해와 근접 공격 피해를 해당 적의 공격력 기준으로 적용하고, 예고·회복 중에도 접촉 피해를 유지한다.
- [ ] 근접 공격을 추격 로직에 직접 넣지 않고 별도 컴포넌트로 분리해 프리팹 단위로 적용한다.
- [ ] 추격과 공격이 같은 이동 제어를 다투지 않도록 이동 금지 판정을 공유한다.
- [ ] 플레이어를 지속적으로 추적하되 공통 피격 무적 시간으로 접촉 피해의 연속 중첩을 방지한다.

추적형끼리의 위치 겹침은 허용하며, 개체 간 분리 이동은 이번 달 필수 작업에 포함하지 않는다.

### 원거리형 변형 — 롱레인지 저격형

- [ ] 전투 정체성을 "멀리서 멈춰 쏘고 파고들면 약한 적"으로 확정한다.
- [ ] 기존 원거리형을 보존하고 저격형을 원거리형의 변형으로 추가한다.
- [ ] 재배치 → 정지 조준 → 발사 → 회복 사이클을 반복한다.
- [ ] 재배치 중 앞뒤 거리 조절과 필요에 따른 좌우 이동으로 다음 사격 위치를 선택한다.
- [ ] 플레이어가 정지해 있어도 사이클에 따라 재배치하되, 좌우 이동을 항상 강제하지 않는다.
- [ ] 이동 중에는 발사하지 않고 발사할 때는 정지한다.
- [ ] 가까운 거리라는 이유만으로 사격 시작을 금지하지 않는다.
- [ ] 사격 전 조준 방향과 발사 시점을 읽을 수 있는 예고를 제공한다.
- [ ] 발사 후 짧은 경직을 두어 플레이어가 거리를 좁힐 기회를 만든다.
- [ ] 후퇴 속도를 플레이어 이동 속도보다 느리게 두어 무한 도주를 막는다.
- [ ] 일정 시간마다 이동 방향을 재평가하고 벽이나 다른 적에게 막히면 좌우 방향을 뒤집는다.
- [ ] 구석에 몰린 상황을 별도 상태로 만들지 않고 좌우 성분과 방향 재선택으로 해소한다.
- [ ] 사거리는 대형 방에서 검증하고 기존 방에는 배치하지 않거나 사거리를 줄인 변형을 사용한다.

> 저격형의 빈틈은 매번 한 번에 처치할 수 있게 보장하는 것이 아니라 조준·발사·회복 사이에
> 거리를 좁히고 공격할 기회다. 후퇴 속도와 플레이어 이동 속도의 차이, 재배치 시간과 정지 시간을
> 함께 조율해 현재 4방향 사격으로 접근과 명중 기회가 생기는지 확인한다.

### 돌진형

- [ ] 기존 예고 → 돌진 → 회복 상태를 보존하고 경계 상태와 연결한다.
- [ ] 예고 중 돌진 경로와 고정된 방향을 명확하게 표시한다.
- [ ] 벽 충돌 또는 돌진 종료 후 플레이어가 공격할 수 있는 빈틈을 강화한다.
- [ ] 벽에 얕은 각도로 스친 경우 즉시 정지하지 않고 제한 시간 또는 거리만큼 접선 방향으로
  미끄러지게 할지 검증한다. 정면 충돌·모서리 충돌은 즉시 정지하고 벽 관통과 떨림을 허용하지 않는다.
- [ ] 돌진 거리와 방 크기의 비율을 대형 방 도입 후 다시 확인한다.

> 여러 돌진형의 동시 돌진은 방향이 예고 시작 시점에 고정되어 대체로 회피 가능하므로 사전
> 차단 대상으로 두지 않고 16주차 플레이테스트 관찰 항목으로 옮긴다.

### 층별 보스

- [x] 1·2·3층 보스를 각각 새마음금고·부스러기·크레용사용으로 선정한다. ([요정왕국 적·보스 선정 및 구상](./18-fairy-kingdom-enemy-boss-plan.md), 2026-09-17)

- [ ] 각 보스에 최소 3개의 행동 또는 공격, 예고, 대응 방법과 공격 후 빈틈을 정의한다.
- [ ] 1층은 기본 패턴 학습, 2층은 공간과 패턴 조합, 3층은 페이즈 전환과 복합 대응을 목표로 한다.
- [ ] 최종 보스는 최소 한 번의 페이즈 또는 패턴 조합 변화를 갖는다.
- [ ] 보스 캐릭터 선정 전에는 구체적인 패턴 구현을 확정 완료로 처리하지 않는다.

> 2층 부스러기, 3층 크레용사용을 사용한다. 일반 적은 불효자손·산사모·저혈당 요정·고혈당
> 요정을 기존 세 AI 역할에 연결한다. 상세 범위와 후속 테마 후보는
> [요정왕국 적·보스 선정 및 구상](./18-fairy-kingdom-enemy-boss-plan.md)을 따른다.

# 9. 16주차 — 선택 보상과 종합 플레이테스트

## 목표

아티팩트를 무작위로 하나 받는 흐름을 후보 비교와 선택으로 바꾸고, 여러 Room·Encounter·적·보스가
포함된 전체 Run을 반복해 전투와 빌드 선택의 재미를 검증한다.

## 필수 작업

### 아티팩트 선택 보상

- [ ] 보물방과 1·2층 보스 처치 후 아티팩트 후보 3개를 표시한다.
- [ ] 각 후보에 이름, 등급, 효과, 현재 스택과 최대 스택을 표시한다.
- [ ] 현재 활성 상태이고 최대 스택이 아닌 아티팩트만 후보에 포함한다.
- [ ] 후보 하나를 선택하면 나머지 후보를 제거하고 선택한 아티팩트만 적용한다.
- [ ] 획득 가능한 후보가 부족한 경우 후보 수 축소 또는 회복 대체 규칙을 확정한다.
- [ ] 회복 대체 보상은 현재 HP와 최대 HP를 표시하고 선택 결과를 즉시 반영한다.
- [ ] 선택 중 전투 입력, 방 이동과 다음 층 이동을 차단한다.
- [ ] 재방문하거나 선택 입력을 반복해도 보상이 중복 지급되지 않는다.
- [ ] 같은 seed에서 후보까지 재현할지, 보상 진입 시 별도 결정값을 사용할지 계약을 확정한다.
- [ ] 선택한 아티팩트만 기존 획득 순서와 Run 결과에 기록한다.

### 보상 UI와 입력

- [ ] 마우스와 키보드로 세 후보를 이동하고 하나를 확정할 수 있다.
- [ ] 선택된 카드와 선택 불가능한 상태를 색상 외 표현으로 구분한다.
- [ ] 긴 효과 설명과 최대 스택 표기가 `1920 × 1080`에서 잘리지 않는다.
- [ ] 선택 후 HUD의 아티팩트와 스탯 변화가 즉시 갱신된다.

### 전체 Run 플레이테스트

- [ ] 서로 다른 seed로 전체 3층 Run을 반복한다.
- [ ] 기존 방과 대형 방의 이동 시간, 피격량과 전투 밀도를 비교한다.
- [ ] Encounter별 클리어 시간과 주된 피격 원인을 기록한다.
- [ ] 감지 거리 밖 공격, 문 주변 공격과 spawn 안전지대 악용 여부를 확인한다.
- [ ] 적 조합에 회피 불가능하거나 지나치게 수동적인 상황이 없는지 확인한다.
- [ ] 여러 돌진형의 동시 돌진이 실제로 회피 불가능한지 관찰하고 필요할 때만 조정한다.
- [ ] 저격형의 멈춤·발사·경직 사이클에서 플레이어가 실제로 거리를 좁힐 수 있는지 확인한다.
- [ ] 추적형의 접촉 피해와 근접 공격 중 어느 쪽이 주된 피격 원인인지 구분해 기록한다.
- [ ] 보스 패턴별 피격 원인과 공격 기회가 명확한지 확인한다.
- [ ] 후보 선택이 현재 빌드와 이후 플레이 방식을 실제로 바꾸는지 확인한다.
- [ ] 거의 선택되지 않거나 항상 선택되는 아티팩트를 기록하고 원인을 구분한다.
- [ ] 한 Run의 10~15분 목표와 층별 소요 시간을 측정한다.
- [ ] 클리어와 사망 Run이 한 번만 저장되고 결과·Web 통계에 반영되는지 확인한다.

### 회귀 검증

- [ ] Backend의 사용자 등록·진행·Run 관련 Jest 테스트와 `pnpm build`를 통과한다.
- [ ] Web 계약을 변경했다면 `pnpm lint`와 `pnpm build`를 통과한다.
- [ ] Unity의 Room 생성 결정성, 재방문 상태, 스킬, 아티팩트와 Run 저장 검증을 통과한다.
- [ ] 자동 검증이 어려운 UI와 체감 항목은 정확한 메뉴 경로, 입력과 기대 결과를 기록한다.
- [ ] 실제 플레이 증거가 없는 밸런스·체감 항목은 완료 처리하지 않는다.

## 완료 조건

> 신규 또는 기존 로컬 플레이어가 홈에서 Run을 시작하고, 정보를 확인하며 다양한 크기의 방과
> 적 조합을 공략하고, 보상을 비교해 빌드를 선택하고, 최종 결과를 저장할 수 있다. 여러 seed의
> 전체 Run에서 심각한 진행 차단, 회피 불가능한 조합과 중복 보상이 발견되지 않는다.

## 10. 에셋 제작과 적용 원칙

에셋은 사용자가 직접 준비하되 구현 전에 용도와 크기를 합의한다. 에셋 제작 때문에 기능 검증을
막지 않으며, 임시 에셋으로 화면과 전투를 먼저 확인한 뒤 교체한다.

### 우선 제작할 기능성 에셋

- 홈 화면 임시 배경과 게임 로고
- HP·SP·저학년·고학년 스킬 아이콘
- 아티팩트 아이콘과 선택 카드에 필요한 등급 표현
- 적 공격 범위, 조준 방향과 돌진 경로 예고
- 피격·회복·SP 획득·무적 상태 표현
- 보스 HP와 페이즈 구분 요소
- 장애물과 방 크기를 구분하는 간단한 타일
- 버튼·패널·팝업의 기본 UI 구성 요소
- 최소한의 피격·회복·선택·보스 공격 효과음

### 에셋 명세에 포함할 정보

- 사용 화면과 용도
- 권장 픽셀 크기와 비율
- 투명 배경 여부
- 기본·호버·선택·비활성 상태
- 9-slice 적용 여부와 테두리 영역
- 파일명과 Unity 저장 위치
- Pixels Per Unit과 필터 설정
- 애니메이션이 필요할 경우 프레임 크기와 수

### 후순위 에셋

- 캐릭터·몬스터·보스 정식 스프라이트 전체 교체
- 정식 방 배경과 대규모 타일 세트
- 고품질 VFX와 화면 전환 연출
- 전체 BGM과 상황별 사운드 완성

## 11. 플레이테스트 기록 기준

넷째 달의 완료 판단은 구현 수가 아니라 실제 플레이 변화에 둔다. 최소한 다음 내용을 기록한다.

| 항목 | 확인 목적 |
|---|---|
| Room Profile별 이동·클리어 시간 | 방이 넓기만 하고 비어 있지 않은지 확인 |
| Encounter별 피격량과 사망 원인 | 적 조합의 공정성과 위협도 확인 |
| 적 유형별 공격 성공·회피 체감 | 역할과 대응 방법 구분 |
| 보스 패턴별 피격 원인 | 예고와 안전지대 검증 |
| 아티팩트 후보와 실제 선택 | 선택 편향과 사장된 효과 확인 |
| 층별·전체 Run 시간 | 10~15분 목표 확인 |
| 네트워크 성공·실패와 재시도 | 결과 저장 안정성 확인 |

플레이테스트 텔레메트리 자동화는 [13-development-tooling-plan.md](./13-development-tooling-plan.md)의
T4 범위와 연결한다. 자동 수집이 이번 달 기능을 지연시키면 먼저 수동 기록으로 근거를 남긴다.

## 12. 일정이 밀릴 때의 축소 순서

다음 순서로 범위를 줄인다.

1. 홈과 전투 UI의 장식·전환 애니메이션을 제외한다.
2. 실패한 Run의 재실행 후 로컬 재전송을 제외한다.
3. 기둥·장애물 Room Profile을 제외한다.
4. 2배 보스방을 제외하고 기존 방과 1.5배 방만 유지한다.
5. Encounter 수를 줄이되 혼합 조합과 웨이브를 각각 하나 이상 유지한다.
6. 아티팩트 카드의 연출을 제외하고 텍스트와 아이콘으로 비교한다.

다음 항목은 축소하지 않는다.

- 타이틀 → 로컬 프로필 → 홈 → 캐릭터 선택 → Run의 기본 흐름
- Game Scene과 Frontend의 분리
- HP·SP·스킬·아티팩트·진행 상태 HUD
- 기존 Room 보존과 대형 Room Profile 1종 검증
- 방 전투 시작 또는 피격 후 적의 지속 경계 상태
- 일반 적 3종의 구분되는 이동·공격·빈틈
- 아티팩트 후보 비교와 1개 선택
- 보상 중복 방지와 전체 Run 회귀 검증

보스 3종의 세부 패턴은 선정이 늦어질 경우 임의로 대체하지 않는다. 선정된 보스부터 계약과 구현을
완료하고, 남은 보스의 미정 상태와 다음 실행 순서를 명확하게 기록한다.

## 13. 다음 계획 후보

넷째 달의 전투 가독성, Room Profile, Encounter와 선택 보상이 검증된 뒤 다음 후보를 검토한다.

- 플레이어 쓰러짐 → `GAME OVER` → 사용자 확인 → 사망 결과 화면으로 이어지는 종료 연출

- 현재 방 중심으로 이동하고 바깥 방을 자연스럽게 자르는 미니맵 뷰포트와 우측 HUD 재배치
- 수작업 Room Layout 기반 장애물·함정과 제한적 배치 랜덤화
- 좁은방·넓은방·일자방·ㄱ/ㄴ자방·초대형 방 등 형태가 다른 Room Template
- 직사각형 계약으로 해결하기 어려운 ㄱ/ㄴ자방의 다중 카메라 구역과 구역 간 보간
- 상점과 엘리프 경제
- 열쇠와 잠긴 보물방
- 폭탄과 파괴 가능한 벽, 이벤트방·비밀방
- 새로운 일반 적과 Encounter 확장
- 보스 추가 또는 기존 보스 고도화
- 아티팩트와 시너지 확장
- 정식 캐릭터·몬스터·보스·방 에셋 적용
- BGM, 효과음과 전투 연출
- 게임 빌드와 배포 준비

다섯째 달 범위는 넷째 달 플레이테스트에서 확인된 가장 큰 반복성 문제를 기준으로 정하며,
기능 목록을 미리 모두 필수 범위로 확정하지 않는다.

### 확정 후속 UX — 일시정지·사망·아티팩트

아래 항목은 이번 Setting-1C 작업에 포함하지 않고 별도 검증 가능한 조각으로 구현한다.

- [ ] 일시정지 메뉴에 `설정`을 추가하고, 설정 화면을 열고 닫는 동안 `Time.timeScale = 0`과
  팝업 내부 포커스 제한을 유지한다.
- [ ] 인게임 설정은 Frontend와 같은 `LocalSettings`를 사용한다. 음량과 상세 스탯 HUD는 즉시
  반영하고, 화면 모드·해상도 변경 후에도 일시정지 계층과 복귀 포커스가 깨지지 않는지 확인한다.
- [ ] 플레이어 HP가 0이 되면 조작·적 공격·투사체·Encounter 진행을 먼저 막되, 캐릭터 쓰러짐
  모션과 필요한 카메라·UI 연출은 끝까지 재생한다.
- [ ] 쓰러짐 모션 완료 뒤 전투 화면 위에 `GAME OVER` 에셋과 `결과 보기` 또는 `다음` 입력을
  표시하고, 자동 시간 경과만으로 결과 화면으로 넘어가지 않는다.
- [ ] 사망 결과 저장은 기존 `clientRunId`로 한 번만 시작할 수 있지만, Frontend 결과 화면 전환은
  사용자가 위 확인 입력을 한 뒤 수행한다. 저장 지연·실패도 같은 요청으로 재시도한다.
- [ ] 획득 전 아티팩트의 바깥 감지 범위에 들어오면 이름·희귀도·핵심 효과를 표시하고 범위를
  벗어나거나 획득하면 숨긴다. 여러 후보가 가까우면 가장 가까운 하나만 표시한다.
- [ ] 아티팩트 이름 색은 희귀도와 연결하되 색만으로 구분하지 않고 희귀도 텍스트나 표식을 함께
  제공한다. 자동 획득을 유지할지 별도 상호작용 입력으로 바꿀지는 구현 전에 확정한다.

권장 의존성 순서는 `인게임 설정 → 사망 종료 연출 → 아티팩트 근접 설명 → 미니맵·HUD 재배치`다.
앞의 두 작업은 기존 HUD-7과 Flow-5를 확장하고, 아티팩트 설명은 선택 보상 전에 정보 표현 규칙을
재사용할 수 있게 먼저 확정한다.

### 확정 후속 UX — 현재 방 중심 미니맵과 우측 HUD

- [ ] 미니맵은 층 전체가 항상 들어오도록 축소하지 않고, 현재 방을 밝은 표식으로 강조해 뷰포트
  중심 또는 중심에 가까운 위치로 부드럽게 이동한다.
- [ ] 뷰포트 밖의 방은 마스크로 자연스럽게 잘라 표시하며, 긴 방이나 큰 방의 실루엣도 경계에서
  일부만 보일 수 있게 한다. 현재 방 전환 때 전체 지도가 순간 이동하는 느낌은 피한다.
- [ ] 현재의 사각 격자 노드는 그대로 지원하되, 이후 Room Template의 폭·높이·형태 데이터를
  미니맵 실루엣에 반영할 수 있도록 표시 계약을 분리한다.
- [ ] Small·Basic·Wide·Tall·Large의 크기와 종횡비 차이가 작은 마커에서도 더 분명하도록 최소
  크기, 테두리, 현재 방 강조와 문 위치 표식을 함께 비교한다.
- [ ] 보유 아티팩트 HUD는 좌하단에서 우상단 미니맵 아래로 옮긴다. 최대 10종과 `+N` 규칙을
  유지하고 향후 코인·폭탄·열쇠 영역과의 세로 우선순위를 다시 정한다.
- [ ] 1280×720에서도 미니맵·아티팩트·스킬 HUD가 겹치거나 중앙 전투 영역을 과도하게 가리지
  않는지 확인한다.

### 우선 예정 작업 — Room Layout과 장애물·함정

넷째 달에 검증한 방 크기와 적 행동을 바탕으로, 다섯째 달에는 지형에 따라 이동 경로와 공격
방법을 선택하는 전투를 실험한다. 기본 방향은 다음과 같다.

| 구성 | 제작·선택 방식 |
|---|---|
| Room Layout | 벽·출입구·통로를 수작업으로 배치 |
| 장애물·함정 | 기본 위치와 회피 공간을 수작업으로 설계 |
| 일부 장식·파괴물 | 미리 지정한 안전한 후보 위치에서 랜덤 활성화 |
| 적 종류·조합 | 해당 Layout에 맞는 Encounter 후보 중 랜덤 선택 |
| 일부 SpawnPoint | 선택한 Encounter에 적합한 지점 또는 spawn group을 랜덤 활성화 |

- [ ] Room Profile의 방 크기·카메라 계약과 연결되는 수작업 Room Layout을 구성한다.
- [ ] 좁은방·넓은방·가로/세로 일자방·ㄱ자방·ㄴ자방·초대형 방을 Room Template 후보로 만들고,
  출입구 조합과 이동 가능한 영역을 수작업으로 검증한다.
- [ ] 직사각형이 아닌 방은 하나의 연결된 이동 영역과 카메라 경계, Encounter 영역, 미니맵
  실루엣을 함께 제공한다.
- [ ] 세로로 긴 방 한쪽에 작은 방 두 개가 연결되는 구성을 실험한다. 방향당 연결 하나 대신
  `left-upper`, `left-lower` 같은 안정 port ID를 사용하고 문 슬롯·안전 진입점·미니맵 선도 같은
  포트를 참조하게 한 뒤 기존 단일 문 방과의 호환 방식을 정한다.
- [ ] 한 화면에 다 들어오지 않는 긴 방·초대형 방에서는 카메라가 플레이어를 따라가되 방 경계
  밖을 비추지 않도록 제한하고, 방 전환 시 다음 방의 카메라 규칙으로 부드럽게 넘긴다.
- [x] 직사각형 Small·Basic·Wide·Tall·Large는 14주차의 축별 카메라 계약으로 먼저 구현한다. (Room-6 Unity 배치 카메라·Prefab 검증, 2026-09-16)

### 구현 전에 정할 규칙

아래 항목은 미정이며 다섯째 달의 상세 계획에서 확정한다.

- [ ] 장애물별로 플레이어·적·투사체·돌진 중 무엇을 막는지 정한다.
- [ ] 파괴물별로 누가 어떤 공격으로 파괴할 수 있는지, 파괴 후 통로 개방과 드롭 여부를 정한다.
- [ ] 함정의 작동 조건·예고·위험 구간·안전 시간과 플레이어·적 피해 여부를 정한다.
- [ ] 함정이 전투 종료 후에도 작동하는지, 재방문 시 작동 상태를 어떻게 처리할지 정한다.
- [ ] 장식과 전투 지형을 구분하고, 랜덤 활성화 수·확률·동시 배치 제한을 정한다.
- [ ] 적 이동과 저격 사선, 돌진이 장애물에 막혔을 때의 행동을 정한다.
- [ ] 첫 구현의 장애물·파괴물·함정 종류와 Layout 수는 넷째 달 플레이테스트 결과에 맞춰 정한다.

### 탐색·소모 자원 확장 후보와 결정 사항

상점·열쇠·폭탄·비밀방은 서로 연결되는 확장 후보이며, 전부를 다섯째 달 필수 작업으로
확정한 것은 아니다. 아래 규칙을 정한 뒤 구현 범위와 순서를 확정한다.

- [ ] 상점: 엘리프 획득·소비·Run 종료 시 유지 여부, 상품 후보·가격·재고와 구매 상태 보존을 정한다.
- [ ] 열쇠: 획득 경로·보유 한도·소비 대상과 잠긴 방을 열지 못했을 때의 진행 규칙을 정한다.
- [ ] 폭탄: 획득 경로·보유 한도·설치 입력·폭발 예고·범위·피해 대상과 파괴 가능한 지형을 정한다.
- [ ] 비밀방: 생성·인접 조건, 발견 단서, 진입 수단과 보상을 정한다. 폭탄 벽을 사용할지도 함께 확정한다.
- [ ] 소모 자원이 없어도 필수 진행 경로를 완료할 수 있는지 확인하고, 선택 보상 접근 조건과 구분한다.
- [ ] 잠금 해제·구매·폭탄 소비·벽 파괴·보상 수령 상태를 재방문 시 보존하고 중복 소비·지급을 방지한다.
