# Trickal Feature Cycle

TrickalFanGame에서 계획된 기능 하나를 검증 가능한 수직 조각으로 완성한다. 주차 날짜보다 문서에 명시된 시스템 의존성과 필수 범위를 우선한다.

## 시작점 확정

1. 저장소 루트와 적용되는 `AGENTS.md`를 확인한다. 모든 텍스트 파일과 텍스트 입출력은 UTF-8을 명시한다.
2. `git status --short`로 기존 변경을 확인하고 사용자 변경을 보존한다. 관련 파일과 겹치면 내용을 먼저 이해한 뒤 최소 범위로 편집한다.
3. 사용자가 지정한 기능과 완료 조건을 우선한다. 사용자가 단순히 다음 작업을 요청했다면 다음 순서로 근거를 찾는다.
   - 현재 실행 계획: `docs/10-second-month-plan.md`
   - 스킬·전투·방 전환의 의존성: `docs/12-skill-system-plan.md`의 구현 우선순위
   - 장기 범위: `docs/02-roadmap.md`
4. 현재 작업에 필요한 문서만 추가로 읽는다.
   - 게임 규칙이나 밸런스: `docs/03-game-design.md`
   - 계층 구조나 데이터 흐름: `docs/04-architecture.md`, `docs/08-project-structure.md`
   - DB 또는 API 계약: `docs/06-database.md`, `docs/07-api.md`
5. 구현 전에 이번 조각의 입력, 상태 변화, 출력과 관찰 가능한 완료 조건을 짧게 확정한다. 계획 문서가 충돌하면 더 최근에 확정된 의존성 문서를 우선하고 충돌을 알린다.

## 범위 결정

- 한 번에 검증할 수 있는 가장 작은 기능 단위를 선택하되, 완료 조건을 만족하는 데 필요한 연결 작업은 포함한다.
- 필수 범위가 안정되기 전에는 선택 작업, 폴리싱, 랜덤화로 범위를 넓히지 않는다.
- 코드가 이미 요구사항을 만족하는지 먼저 확인하고 중복 구현하지 않는다.
- 계약이나 공용 기반을 바꾸는 작업은 소비자를 검색해 영향 범위를 확인한다. Unity, Backend, Web 가운데 실제로 영향을 받는 계층만 수정한다.
- 사용자의 요청이 설명, 검토 또는 진단뿐이면 구현하거나 체크리스트를 변경하지 않는다.

## 구현 규칙

### 공통

- 기존 네임스페이스, 폴더, 명명 방식과 책임 분리를 따른다.
- ID는 영문 안정 키로 취급한다. 기존 Item, Character 또는 Run 관련 ID의 의미를 바꾸거나 재사용하지 않는다.
- 상태 전환과 Run 종료처럼 중복 호출될 수 있는 경로는 멱등성 또는 재진입 방지를 확인한다.
- 새 추상화는 현재 기능과 가까운 후속 기능에서 실제로 재사용될 때만 도입한다.

### Unity

- 런타임 규칙을 Editor Setup 코드에 숨기지 않는다. Setup 코드는 씬, 프리팹, ScriptableObject와 직렬화 참조를 구성하는 역할로 제한한다.
- 반복적인 씬·에셋 구성이 필요하면 기존 `game/Assets/Editor/Week*Setup.cs` 패턴을 참고한다. 재실행 시 중복 오브젝트나 에셋을 만들지 않고, 가능한 경우 Undo와 dirty/save 처리를 제공한다.
- 검증 코드는 결과를 사람이 눈으로 추측하게 하지 말고 핵심 불변조건 실패 시 명시적으로 실패하게 한다. 기존 `Week6ItemVerification.cs`처럼 양방향 순서, 중복 실행, 상한, 상태 유지 등 요구사항의 경계도 확인한다.
- Scene 또는 Prefab 텍스트를 직접 대규모 수정하기 전에 Editor 구성 코드나 작은 직렬화 변경으로 해결할 수 있는지 검토한다.
- Unity가 생성하는 `.meta` 파일과 GUID 참조를 보존한다.

### Backend와 Web

- Prisma 스키마, 마이그레이션, seed, DTO, 서비스, 저장소와 테스트 중 실제 계약 변경에 필요한 부분을 함께 확인한다.
- Run 저장, 보상, 경험치처럼 중복 지급 위험이 있는 작업은 트랜잭션 경계와 재전송 동작을 검증한다.
- API 응답 또는 필드가 바뀌면 Unity DTO와 Web 소비 코드를 검색해 계약 드리프트를 확인한다.

## 검증

1. 변경 위험에 비례해 가장 가까운 자동 검증부터 실행한다.
   - Backend: 관련 Jest 단위 테스트, 필요 시 e2e, build 또는 lint
   - Web: lint와 build 중 변경을 실제로 검증하는 명령
   - Unity: 관련 Editor Verification 또는 Unity Test Runner, 컴파일 확인
2. Unity Editor를 직접 실행하거나 로그를 읽을 수 없다면 그 사실을 숨기지 않는다. 가능한 정적 검사를 수행하고 사용자가 실행할 정확한 메뉴와 기대 결과를 남긴다.
3. 생성기와 검증기를 추가했다면 정상 경로뿐 아니라 재실행, 누락 참조, 중복 상태 등 해당 기능의 대표 실패 경로를 확인한다.
4. 테스트 실패를 기존 실패로 단정하지 않는다. 변경 전 상태나 관련 로그로 근거를 확보하고, 이번 변경 때문이면 수정한다.
5. 자동 검증이나 사용자가 제공한 수동 확인 증거가 있는 항목만 계획 문서에서 `[x]`로 바꾼다. Unity 수동 확인이 남았다면 해당 항목을 완료 처리하지 않는다.

## 마무리

- 구현한 결과를 먼저 요약한다.
- 변경 파일과 각 파일의 역할을 정리한다.
- 실행한 검증과 결과를 구체적으로 적는다.
- 실행하지 못한 Unity 수동 검증은 메뉴 경로, 조작, 기대 결과를 포함한 짧은 체크리스트로 제공한다.
- 남은 위험과 다음 의존 작업을 구분한다. 안전한 다음 작업이 명확하면 제안하되 자동으로 범위를 확장하지 않는다.
