# Trickal Obsidian Journal

완료된 작업을 나중에 다시 활용할 수 있는 근거 중심 기록으로 남긴다. 저장소의 확정 문서를 복제하지 않고, 구현 과정의 맥락과 판단을 Obsidian에 보존한다.

## 실행 조건

아래 둘 중 하나를 충족할 때만 이 스킬을 사용한다.

1. 사용자가 개발일지, 결정 기록, 회고, 아이디어 기록 등 Obsidian 문서 작성을 명시적으로 요청했다.
2. 기준 계획 문서에서 한 주차의 작업 범위가 완료되었고, 완료 체크와 필요한 검증 근거를 확인할 수 있다.

- 개별 기능, 버그 수정, 단계, PR 또는 대화 한 턴의 완료만으로는 자동 실행하지 않는다.
- 주차 완료 여부가 불명확하거나 검증이 끝나지 않았다면 자동 실행하지 않는다. 필요한 작업을 먼저 마친 뒤, 주차가 끝난 시점에 기록한다.
- 사용자가 명시적으로 요청한 경우에는 주차 완료 전에도 해당 요청 범위만 기록할 수 있다.

## 위치와 기준

- 볼트: `C:\Users\yeonguk\Desktop\폴더\Obsidian`
- 프로젝트 홈: `TrickalFanGame/00 프로젝트 홈.md`
- 작성 가이드: `TrickalFanGame/기록 가이드.md`
- 템플릿: `TrickalFanGame/99 Templates`
- 모든 Markdown과 텍스트 입출력은 UTF-8을 사용한다.
- 저장소 `docs/`가 설계, API, 계획, 체크리스트의 원본이다. Obsidian에는 원문을 복사하지 말고 필요한 문서 경로만 연결한다.

## 기록할 근거 확인

1. 현재 대화에서 사용자가 요청한 목표와 실제 완료 결과를 확인한다.
2. `git status --short`로 기존 사용자 변경과 이번 작업의 변경을 구분한다. 관련 diff, 테스트 결과, 수동 검증 증거와 작성된 문서를 필요한 만큼만 읽는다.
3. 완료라고 적을 수 있는 범위를 검증 근거와 맞춘다. 실행하지 못한 검증은 완료로 꾸미지 않고 `아직 확인하지 못한 부분`에 기록한다.
4. 구현 전부터 존재한 변경이나 다른 작업자의 결과를 이번 작업이 만든 것으로 주장하지 않는다.
5. 의미 있는 결과나 재사용할 배움이 없으면 문서를 억지로 만들지 말고 기록하지 않은 이유를 알린다.

## 문서 선택

실행 조건을 충족했다면 개발일지 하나를 기본으로 만든다. 나머지는 아래 조건을 실제로 충족할 때만 추가한다.

| 조건 | 위치 | 템플릿 | 파일명 |
| --- | --- | --- | --- |
| 명시 요청 또는 검증된 주차 작업 완료 | `01 개발일지` | `개발일지 템플릿.md` | `YYYY-MM-DD 구체적인 작업명.md` |
| 대안 사이에서 구현 방향이나 범위를 선택 | `02 결정 기록` | `결정 기록 템플릿.md` | `DEC-NNN 결정 제목.md` |
| 해결에 오래 걸렸거나 재발 가능성이 있는 문제 해결 | `03 문제 해결` | `문제 해결 템플릿.md` | `문제의 증상이 드러나는 제목.md` |
| 검증된 주차 작업 완료 | `04 회고` | `주간 회고 템플릿.md` | `YYYY-Www 주간 회고.md` |
| 가치가 있지만 현재 범위에서 미룬 구체적인 생각 | `05 아이디어 보관함` | `아이디어 템플릿.md` | `아이디어 제목.md` |

- `DEC-NNN`은 `02 결정 기록`의 기존 파일을 확인하여 가장 큰 번호 다음 값으로 정한다. 번호 충돌이나 기존 문서 덮어쓰기를 허용하지 않는다.
- 동일 작업의 기록이 이미 있으면 새 파일을 만들기보다 기존 문서를 보완한다.
- 하나의 사건을 여러 문서에 반복해서 길게 적지 않는다. 개발일지는 결과 요약과 관련 기록 링크를 담고, 상세 판단이나 해결 과정은 전용 문서에 둔다.

## 작성 원칙

- 템플릿의 질문은 유지하되 답이 없는 항목은 추측하지 않는다. 의미 없는 빈 절은 제거할 수 있다.
- 변경 파일 목록보다 사용자에게 보이는 결과, 핵심 구조, 검증 증거, 다음 행동을 우선한다.
- 문제 해결 문서에는 증상, 재현 조건, 원인, 실패한 접근, 최종 해결과 확인 방법을 구분한다.
- 결정 기록에는 실제로 검토한 선택지만 적고, 선택 이유와 감수한 단점, 다시 검토할 조건을 남긴다.
- 회고는 계획 대비 차이의 원인과 다음 주 행동을 포함한다.
- 아이디어는 MVP 필수 작업과 구분하고 다시 검토할 조건을 명시한다.
- 비밀, 토큰, 개인식별정보, 로컬 환경의 민감한 값은 기록하지 않는다.

## 파일 생성과 색인

1. 대상 폴더의 안내 문서와 선택한 템플릿을 먼저 읽는다.
2. 대상 파일이 없는지 정확한 경로로 확인한다.
3. 환경 정책상 볼트에 직접 편집할 수 없다면 저장소의 임시 전용 폴더에 `apply_patch`로 파일을 작성하고, 볼트로 복사하기 직전에 필요한 쓰기 승인을 요청한다. 다른 우회 경로를 사용하지 않는다.
4. 생성 후 UTF-8로 다시 읽어 제목, 날짜, 내부 링크와 핵심 내용을 확인한다.
5. 해당 폴더의 안내 문서 `기록 목록`과 `00 프로젝트 홈.md`의 맞는 최근 기록 구역에 상대 위키 링크를 추가한다. `아직 없음`은 첫 링크를 넣을 때 제거하고, 같은 링크를 중복 추가하지 않는다.
6. 임시 파일을 만들었다면 검증 후 정리한다. 저장소의 다른 변경은 건드리지 않는다.

## 마무리 보고

- 생성하거나 갱신한 문서의 종류와 제목을 먼저 알린다.
- 각 문서가 기록한 핵심을 한 문장씩 요약한다.
- 문서를 만들지 않은 범주가 있다면 전부 열거하지 말고, 사용자가 기대했을 법한 항목만 간단히 이유를 설명한다.
- 저장소 문서에 별도로 반영해야 할 확정 정보가 발견되었다면 제안하되, 사용자가 요청하지 않은 저장소 변경까지 자동으로 확장하지 않는다.
